## 1. ✅ 共識規則(5 家以上一致 —— 照做)

### R1|內容底是近白,不是灰也不是深色
十家的主背景全部落在 **246–255** 區間。**零例外。**
⚠️ 修正:先前寫「都是 `#fcfcfc`」是量化假象(我的統計把 246–255 塌成一格)。正確是「都在極亮區間」。
→ **內容面 `#ffffff`;應用底 / 表頭 / 次階面用 `#f6f8fa`–`#f9fafb`。**

### R2|🔴 瀏覽用表格只畫水平線;可編輯的明細畫完整格線
**六家一致**,而且每一家都是**同產品內兩種待遇**:

| 家 | 瀏覽清單 | 可編輯 |
|---|---|---|
| Odoo | 無垂直線 | 樞紐矩陣**有**完整格線 |
| Metabase | 逐像素掃描 **0 條** | — |
| Directus | 無(表頭 2px) | — |
| Ragic | 資料列無(表頭有) | 設計器畫布=**試算表 + 列號** |
| D365 | 清單 grid **0 條** | 設定型 grid **9 條 `#EBEBEB`** |
| ERPNext | 無 | **子表完整格線 + 列號欄 + 逐列鉛筆** |
| NocoDB | — | 可編輯網格**有**(但極淡 `#F7F8F8`) |

→ **格線是「這一格可以點進去改」的訊號,不是後台的證據。**
⚠️ NocoDB 自己被批評「格線過淡,密集數字欄近乎無分隔」→ 我方格線要**看得見**。

### R3|無 resting 陰影,靠 1px 細框分層
**九家一致**(Odoo / Ragic / Metabase / Directus / D365 / ERPNext / NocoDB / Qualio / isoTracker)。
陰影只出現在**浮層**(下拉、modal、抽屜)。

### R4|🔴 數字用 tabular 進位,**不換等寬字體**
NocoDB 像素實測:同欄數字起點對齊、「12,000」31px vs「89,000」32px,**但字身與內文同一套比例無襯線**。
其餘五家報告的「未見等寬字」是同一件事。
→ **`font-feature-settings:"tnum"` + 右對齊,不要 `font-family: mono`。**
⚠️ 這推翻我先前每一版 mockup 都把數字設成 IBM Plex Mono 的做法。

### R5|主色不進資料儲存格
十家**沒有一家**用主色當儲存格底。主色只出現在:**主按鈕 · 連結 · 選取態 · active 標示**。
**唯一例外**|選項欄的彩色 chip(NocoDB)—— 而它的顏色是**建表者逐選項指派的固定色**,不是由值推導。

### R6|唯讀欄位用更深一階灰填色
Ragic 值格 `#fafafa` → 唯讀 `#e8e8e8`;isoTracker 白底 → 唯讀 `#E8ECEF`。**兩家獨立一致。**
→ 不用鎖頭圖示、不用灰字。

### R7|按鈕三階
實心(主要,每頁通常只有一個)· 外框或淺填(次要)· 純文字(第三)。八家皆有此結構。

### R8|不用頁碼列(多數)
Metabase / Directus / Ragic **完全沒有**;ERPNext 是 `20/100/500/2500` 分段鍵 + Load More;Odoo 是 `1-24/24` + 箭頭。
**唯一例外 Qualio** 有 `Show [15] ‹ Page 1 ›`。
→ 筆數一定要顯示;頁碼可以不要。

### R9|型別圖示:純量灰,關聯才上色
NocoDB:`#` `T` `$` 日曆 核取 一律灰;**link 藍 / rollup 橘 / 多對多 洋紅 / FK 琥珀**。
→ 顏色留給「指向別張表」的語意,不是每個型別都配一色。

### R10|無斑馬紋
十家皆無。列的區分靠 1px 水平線。

## 3. 🔴 三個被推翻的既有認知

### 3.1 Ragic 的「實心分段色條」不是內建功能
`ragic-11` 的設計器左側面板逐字列出「**靜態文字**」六個色票元件:白底深字 / **黑底白字** / 白底藍字 / **藍底白字** / 白底紅字 / **暗紅底白字**。
→ **單據上那些藍色分段條,是使用者自己拖進去的裝飾文字塊。Ragic 沒有 section 概念。**
→ 這是**能力缺口不是設計語言**。Weyver 的 `layout.sections` 是真的分段 —— 這是我方比它強的地方,不是該照抄的東西。
⚠️ `weyver-doc.html` 的分段色條建立在此錯誤前提上。**該稿 2026-08-07 經決策方裁定為現行視覺方向** —— 視覺可以被喜歡,與我當初的理由是否成立是兩件事;理由錯了要記,稿子留不留由決策方定。

### 3.2 沒有任何單一量化指標能分辨「像產品 vs 像後台」
四個都量過:
· **彩色像素比** 3.1%(Directus,像產品)– 22.7%(isoTracker,像後台)
· **深色像素比** 0%(Metabase,像產品)– 14.7%(Qualio,像產品)– 7.3%(isoTracker,像後台)
· **線條密度** Qualio 6.79%(像產品) vs isoTracker 6.40%(像後台)—— **幾乎一樣**
· **主色相** 六家同帶而觀感天差地遠
→ 「加顏色」「加深色」「減框線」都不是答案。

### 3.3 那「舊感」到底來自哪裡?—— 十家報告收斂出的**具體清單**
不是抽象的「不夠現代」,是這些可指認的東西:

| 舊感來源 | 出處 |
|---|---|
| **原生 `<select>` 曝光**(展開是 OS 藍高亮) | isoTracker · Ragic(18 種型別塞一個原生 select) |
| **框架預設外觀未改造**(DataTables 的 `Search:` + `Showing 1 to 3 of 3`) | isoTracker |
| **灰色漸層彈窗標題列** | Ragic(`#cfcfcf`→`#c7c7c7`) |
| **資料夾式立體頁籤 / fieldset+legend / 雙欄穿梭選擇器** | Ragic · isoTracker |
| **ribbon 依「功能來源」而非任務分組** | D365(Office 2007 血統) |
| **同產品內兩代語言並存** | D365(ribbon + Win8 磁磚 + 新版 Copilot)· NocoDB(側欄選取灰 vs 藍、chip 飽和 vs 淡底) |
| **主色隨模組跳** | isoTracker(CAPA 橘 / Documents 金黃)· Ragic(分類頁籤紫/藍/綠/青) |
| **調色盤不成系統**(同頁多套) | ERPNext(至少四套)· Odoo(標籤 pill 隨機粉彩,顏色與內容相反) |
| **字級層級幾乎為零** | isoTracker 1.15–1.3× |
| **圖示多套混用**(線性 + 彩色迷你插畫 + 卡通頭像) | Ragic 三套 · Odoo |
| **主要動作置中 / 頁尾印版本號 / 停用項灰著留在導覽列** | isoTracker |
| **金額被截斷、幣別符號重複、同頁多幣別併存** | ERPNext(`$ 2,00,000.0`、$ ₹ € 併存)· NocoDB(`12,000 $ USD`) |

### 3.4 🆕 Ragic 的頂欄分類不是模組列 —— 而我一度把它畫成模組列
`ragic-03` + `ragic-05` 顯示 Ragic 示範帳號的頂欄分類是:
**報表 · 活動管理 · 庫存 · 訂單管理 · 業務 · 採購 · 人才招募 · `＋`**

兩個可直接抄的作法:
1. **刻意混**|庫存 / 訂單管理 / 採購 是 ERP 味的,但 **活動管理**(活動資訊 / 報到清單)與
   **人才招募** 不是任何 ERP 的模組 —— 這個組合本身就在說「分類是使用者自己開的」。
2. **`＋` 長在頁籤列裡**,永遠看得見。

⚠️ **我方踩過**|`weyver-v1` 初稿把分類寫成 `採購/銷售/生產/庫存/品保/財會` 六個 ERP 模組名,
**並且拿掉了 `＋`**。兩個錯疊起來,結果是一條鼎新式固定模組列 ——
**正好推翻「表單引擎是 substrate,不是模組之一」的定位**。已改為
`採購 · 生產排程 · HACCP 紀錄 · 供應商稽核 · 客訴處理 · 財會 · ＋`。
→ **示範資料本身就是定位宣告**,不是隨手填的假字。

⚠️ **不抄的部分**|Ragic 的分類頁籤是**彩色的**(紫/藍/綠/青),那已列在 §3.3
「主色隨模組跳」的舊感清單裡。我方頁籤維持單色。

**只有一個檢視**。v2 已合併,而 R2 改由 ① 主網格 ② 記錄裡的品項明細子表 兩處兌現。

**不是拆掉目錄**;同時把分類**也**放上頂欄當導覽 —— D3 只講首頁,不衝突。

### 5.5 範本庫詳情 + 關聯圖(2026-08-07 追加)
查驗結果:我方 **8 個 pack / 14 張表**,最大的 pack 3 張;選擇器是 116 行的平鋪 `<ul>`,
只有**一行被 `truncate` 切掉的說明**。Ragic 應用商店側欄**至少 24 個分類**,
「ERP 系統」一個 pack 就含訂單管理 + 庫存 + 採購 + 財會四個模組,右側有整面詳情與**表單關聯圖**。

🔴 **最傷的不是數量,是「看不懂就不敢裝」** —— 範本庫的價值前提是「打開就能用」,
使用者得先相信它能用。故先做詳情面板 + 關聯圖(截圖 `v2-template-store.png`)。

兩個設計主張:
- **關聯圖由 pack 定義推導**(`ref` / `parentRef` / `targetRef` 已是結構化資料),
  不是另外畫的圖 → **不可能和實際裝進去的東西不一致**。
  ⚠️ 不宣稱 Ragic 的是靜態圖(未查證),只陳述我方性質。
- **子表用垂直連接線、連結用水平箭頭,刻意不同形** —— 它們是兩種關係:
  子表是**同一筆記錄的一部分**,連結是**指向另一張表的另一筆**。
- 「套用後會發生什麼」段落 = 所見即後果。對不會寫程式的人,
  按「取得」前最想知道的是**會不會弄壞我現在的東西**。

⚠️ 三個查證出來、尚未處理的缺口:**分類軸完全沒進 UI**(schema 有 `categoryName`/`industry`)·
**`version` 寫了 8 次讀 0 次、也沒有安裝紀錄表** → 「更新」在資料層無從實作 ·
pack 深度只用到 schema 上限 20 的 3。

### 5.6 空狀態(2026-08-08 追加)
截圖 `v2-empty-{home,form}.png`。兩個空狀態:**全新租戶 0 張表** · **表建好了 0 筆記錄**。

🔴 **空狀態是「不用寫 code」這個承諾的第一次兌現。** 新租戶登入後如果看到
「一片空白 + 一顆 ＋」,那句承諾還沒開始生效 —— 他還是得自己想辦法。

**站① 一手依據**|`builder/_components/shell/form-list.tsx:66` 逐字:
「建表的三條路並列:範本 · Excel · 空白。**範本放最前面 —— 對第一次建表的人,
『從範本開始』比空白畫布好下手**。」

🔴 **而現況首頁沒有遵守它。** `app/page.tsx:139` 逐字:
「還沒有表單。點『新增表單』用設計器建立,或從 Excel 匯入。」
—— 一行純文字,**而且漏掉範本**,正好漏掉最適合新手的那一條。
設計器側欄做對了,首頁沒有;而首頁才是新租戶第一個看到的畫面。

**排序理由**|範本 → 已有 Excel → 空白。不是「由簡到繁」,是
**由「別人已經想過」到「你自己想」** —— 第一次建表的人最缺的不是工具,
是「一張表長什麼樣才對」。

**兩條刻意的克制**|① 空狀態**不畫空殼**(0 張表時不渲染情境側欄、不渲染空網格
——「表格右側一大片無主空白欄」在 0 筆時最明顯,一排空格線看起來像壞掉)
② **不畫沒出貨的東西**(AI 建表是第四條路,但 `ai-assist` M3 未出貨 → 不畫,
否則 mockup 會變成願望清單)。

#### 5.6.1 🔴 三張並排卡片 → 清單(2026-08-08 重做)
初稿把三條路畫成三張並排卡片。放大看之後,**每個元素都指不出出處** ——
而那正是 [[feedback-ai-vibe-tells]] 的 **D5 構造規則**要擋的:**指不出=刪**。

| 被刪的 | 為什麼 |
|---|---|
| 圖示放在淡色圓角方塊裡 | 225 張參考圖**沒有一家**這樣做 |
| 「建議」章 | Ragic 的「精選應用」是**分類名**不是章 —— 建議該用**順序**表達 |
| 3px 主色左框線 | 指不出出處 |
| 整寬實心按鈕 | Ragic 應用商店是**右側一顆小的「取得」**(`ragic-03`) |
| 三張並排卡片 | 這是 **AI-SaaS 的預設版式**,不是這個任務的形狀 |

**改用清單,三條依據**|① 站①:我們自己出貨的 builder 側欄(`form-list.tsx:66`)
就是三個並排的**純文字按鈕** —— 空狀態是同樣三個動作,該用同一套語彙
② 共識 R2:瀏覽用清單**只畫水平線**(6/6),而這就是一個瀏覽清單
③ 共識 R7:按鈕三階、實心每頁只給一顆 → 範本實心,另兩個外框。

→ **一般化的教訓:「三張並排卡片」本身就是一個 AI 味 tell。**
它是「有三個選項」時最不用動腦的版式,而正因為不用動腦,它幾乎不會是對的形狀。

⚠️ 225 張參考圖裡**沒有空狀態畫面**,版面全部是 [判斷];唯一有依據的是三條路的排序。

### 5.8 型別圖示四案對照(2026-08-08)
`docs/mockups/_icon-compare.html`(截圖 `icon-compare.png`)。決策方問「有沒有豐富視覺、色彩的元件庫」。

**站②查驗結果**|已裝的只有 `lucide-react 0.469.0`(1748 個,ISC)。
mockup 裡的路徑**是真的 Lucide**(`dollar-sign` 逐字比對相同)。
🔴 **Lucide 沒有系統性填色 / 雙色變體** —— 1748 個裡只有 **7 個**帶 `fill`(實測)。

**兩個反對彩色圖示的理由,不是品味**|
① **物理**:渲染在 14px,多色會糊成一團,顏色資訊消失 —— 可量,不是喜好
② **證據**:共識 R9(NocoDB 重看確認:`T` `#` 迴紋針 信封 電話 **全部單色深灰**)
   + §3.3 把「圖示多套混用」列為**舊感來源**(Ragic 三套 / Odoo)

**四案在 14px 真實尺寸下的觀察**(不是放大看)|
- **A 現況(全灰)** —— 安靜、可讀,但確實沒有存在感
- **B 分組上色** —— 依型別分組給色(不是每個一色),14px 下仍清楚,
  且顏色**承載「這是哪一類」**,對應 §6.2 的替代原則。**最符合決策方的訴求**
- **C Duotone** —— ⚠️ 是用 Lucide **模擬** Phosphor 技法,非真字形(Phosphor 未裝,
  不為對照加相依)。🔴 **14px 下它讀起來像彩色小方塊不像雙色圖示 —— 技法沒有撐過這個尺寸**
- **D 字符化** —— `T ¶ # $ @ ƒx` 明顯比象形清楚(NocoDB 就是這樣混用)。
  🔴 但**只有 6/16 個型別有天然字符**,其餘退回灰象形 → 整欄看起來是混的,
  正好落在 §3.3 警告的「混用」上。零成本零相依是它的優點
- **E · B+D 混合** ✅ **2026-08-08 決策方選定,已套進設計器面板**。
  有天然字符的用字符,其餘用象形 —— **但兩者都吃分組色、同尺寸**。
  🔴 **這一點是關鍵**:D 單獨看是「兩套系統混用」(§3.3 的舊感來源),
  而**一旦共用同一組分組色與同一個字級,它就不是兩套系統,是同一套系統的兩種字身** ——
  就像一份排版裡同時有數字與文字,沒有人會說那是混用。

🔴 **字符化有前提條件,而且是實測出來的,不是查表**:
字體要有那個字符,**而且小尺寸下要可讀**。`№`(自動編號)在 13.5px 的 IBM Plex Mono 下
**糊成一塊不可讀** —— 截圖放大 2.6 倍才看見,已改回象形(`list-ordered`,
語意上也更貼切:自動編號 = 有序序列)。最終字符 **6 個:`T ¶ # $ @ ƒx`**。

**未涵蓋**|11 個設定頁尚未重新設計。

## 6. 🔴 色彩限制解除(2026-08-08 決策方指示)

> 「解除色彩的限制規則,可以大膽、要具有品牌感,禁止『內部後台』排版、色彩」

依 [[feedback-redesign-full-strength]],舊規範降為**產出**不是約束。逐條重審:

### 6.1 我推翻自己的三個判斷

🔴 **① 共識 R5「主色不進資料格」10/10 —— 但那十家正是「後台感」的十家。**
Odoo / D365 / ERPNext / Ragic / NocoDB 全是後台軟體。「10/10 一致」量到的不是
好設計的共識,是**這個品類的共同習慣**,而共同習慣正是後台感的來源。
→ **共識能告訴你「大家都這樣」,不能告訴你「這樣是對的」** —— 當目標正是脫離
這個品類時尤其。這條對 §1 的所有共識規則都成立,是本文件方法論上的一個限制。

🔴 **② 「後台的簽名是左側側欄」判錯了。**
§2 我自己量的:**Qualio 深色側欄 249px 佔畫面 18%,而它被判「像產品」**;
Directus 深色窄軌同理。後台感來自 **四層樹 + 灰白配色 + 四層水平帶**,不是側欄。
v2 選 46px 細頂欄是**過度克制**。

🔴 **③ 把 Ragic 彩色分類頁籤判成舊感,判錯了半條。**
§3.3 我自己的原話是「**調色盤不成系統**(同頁多套)」—— 問題不是分類有顏色。
而 `tokens.css` 早有 **c1–c8 成系統類別色**(字/框/底三值、統一去飽和與明度),
**零 reader**。

### 6.2 替代原則(取代「主色不進資料格」)

> **色彩要承載結構資訊,不是塗上去的。**
> 一格顏色如果回答不了「這是什麼」或「這在哪一區」,它就是裝飾 → 刪。

144 張表單的工作區裡,「我在哪一區」是**真實的認知負擔**,那就是色彩的職責。
分類色**貫穿**:側欄的點 → 表單標題色帶 → 記錄面板頂緣,同一個顏色不斷。
**色彩是導覽。**

### 6.3 三條沒有解除

1. **語意色只屬於狀態**(ok/warn/error)—— 否則「紅」同時代表「退回」與
   「品保分類」,那不是大膽是壞掉。
2. **資料格保持中性** —— 不是沿用舊規則,是新理由:248 列逐格上色是噪音,
   而「在哪一區」已由 chrome 回答過。**chrome 大膽,資料乾淨。**
3. **AI 味清單不解除** —— 決策方解除的是「色彩不夠」,不是「可以加特效」。
   **大膽 = 飽和的平色大面積**,不是漸層 / 光暈 / 玻璃。

### 6.4 ⚠️ v3 方向被否決(2026-08-08)
`weyver-v3.html`(深海青 216px 品牌殼 + 分類色貫穿三站)**經決策方判定方向不對,已刪**。
回到 `weyver-v2.html`。

**§6.1 的三條推翻仍然成立** —— 被否決的是「大面積深色殼 + 分類色」這個**具體解法**,
不是「共識取樣自後台品類」這個方法論觀察。

`WeyverLoginCenterCard.dc.html`(2026-08-08)。已原樣移植進 `weyver-v2.html`,
