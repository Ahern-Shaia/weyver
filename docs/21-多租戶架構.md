# Weyver 多租戶架構(巨人分層)

> **文件性質**|多租戶架構設計。承接「多租戶是否有巨人肩膀」的討論 —— **每一層都有成熟巨人,不自研租戶邏輯**。給五層選型 + subdomain/自訂網域 + 實作鐵則。
> **配套**|docs/11(Better Auth)+ docs/15/16(RLS + shared schema)+ docs/20(DBOS/BullMQ)+ AGENTS.md(租戶 P0 鐵則)。
> **版本**|2026-07-18 v1

---

## 0. 五層巨人總表

| 層 | 職責 | 巨人(採用)| 授權 / ops |
|---|---|---|---|
| **1 DB 資料隔離** | 租戶資料不外洩 | **PostgreSQL RLS**(shared schema + `tenant_id`)| 內建,零額外 |
| **2 context 傳遞** | 每請求 / 非同步帶租戶 | **nestjs-cls** + **@nestjs-cls/transactional**(Knex+Drizzle adapter)| MIT,in-process |
| **3 網域路由 + TLS** | subdomain / 自訂白牌網域 | **Caddy on-demand TLS**(自 host)/ Cloudflare for SaaS(managed)| Apache 2.0 / 付費選配 |
| **4 租戶識別** | 請求 → 哪個租戶(且防偽)| **JWT `tenant_id` claim 為真實來源**(自研中介,標準 pattern)| — |
| **5 auth + authz** | org 管理 + 三層權限 | **Better Auth org/SSO/SCIM**(docs/11)+ 三層授權 in-app（RLS+Guard+mask）| MIT / OSS |

**向上設計**|五層巨人疊起來 = 企業級白牌 + **忘不掉的 DB 層隔離** + 零 JVM,而非 solo 手刻租戶邏輯。

## 1. DB 資料隔離(PostgreSQL RLS)

**三模型**|(a) shared schema + `tenant_id` + RLS(最省,scales 到數千租戶)/(b) schema-per-tenant(強隔離、易 per-tenant 匯出、migration ×N)/(c) db-per-tenant(硬隔離、資料落地、ops 最重)。

**Weyver 策略**|**預設 (a)**;**graduate (b)/(c) 為企業租戶升賣**(合規 / 資料落地 / 深客製時)。因已跑 **Knex 動態表**,schema-per-tenant 是自然升級路徑,不需重架構。(呼應 docs/15/16。)

**RLS pattern**:
```sql
ALTER TABLE invoice ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoice FORCE ROW LEVEL SECURITY;   -- owner 也受約束
CREATE POLICY tenant_isolation ON invoice
  USING     (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK(tenant_id = current_setting('app.tenant_id')::uuid);
```
**未設 context → 查到零列(secure by default)。**

**⚠️ Gotchas(全確認)**|
- **superuser / `BYPASSRLS` 角色略過所有 policy**|app DB 登入角色**不得擁有表、不得有 `BYPASSRLS`**;`BYPASSRLS` 只給 migration 角色;admin 存取用**明確 admin policy**(可審計可撤)而非 privilege bypass。
- **表 owner 略過 RLS**|除非加 `FORCE ROW LEVEL SECURITY`。
- **連線池洩漏 GUC(#1 footgun)**|`SET` 會殘留在實體連線洩漏給下個請求;**用 `SET LOCAL`(交易範圍)** commit/rollback 自動重置 → **相容 PgBouncer transaction mode**。
- **索引**|`tenant_id` 放主要存取索引的**前導欄**(缺複合索引才是效能殺手,非 policy 檢查)。

---

## 2. 租戶 context 傳遞(nestjs-cls)

- **nestjs-cls(AsyncLocalStorage)= 社群標準**|`ClsModule` middleware 每請求 `ALS.run()`,租戶 context 自動傳到 service/repo/promise chain,**不用手動穿參數**。
- **設 RLS GUC**|**@nestjs-cls/transactional**(有 Knex + Drizzle adapter)把每請求包成交易;**該交易第一句 `SET LOCAL app.tenant_id`**(此處手接線 —— plugin 無 on-tx-begin callback,列為唯一手動點)。
- **⚠️ 背景工作(BullMQ / DBOS)**|**ALS 不跨 queue hop** —— worker 另一執行 context,租戶會丟失。**Pattern|enqueue 時把 `tenant_id` 塞進 job payload,worker 重建 CLS + 重下 `SET LOCAL`** 再碰 DB。**不可依賴 ALS 跨佇列。**(→ 直接落實 AGENTS.md 「非同步也傳租戶 context」鐵則。)

---

## 3. subdomain + 自訂網域路由

- **subdomain(`*.weyver.app`)**|wildcard DNS + 一張 wildcard TLS(DNS-01)+ middleware 抽 subdomain → 租戶。最省。
- **自訂白牌網域(`erp.客戶.com`)** 兩選項|
  - **⭐ Caddy on-demand TLS(自 host,Apache 2.0)**|首次 TLS handshake 對未知 hostname 即簽 Let's Encrypt 憑證,由你 host 的 `ask` endpoint 閘控(只對已註冊網域回 200)。首次握手慢(秒級),之後快取自動續。小 VPS 可跑(社群報告單機 36k 網域)。**OSS / solo / 省成本首選**;你自管 rate-limit + HA。
  - **Cloudflare for SaaS(managed)**|custom hostname 為服務,TLS 全託管(CNAME);前 100 免費,之後 $0.10/hostname/月;附 WAF/CDN/DDoS。用錢換零 TLS ops。
- **建議**|subdomain 用 wildcard;自訂網域用 **Caddy on-demand TLS**,規模化再考慮 Cloudflare for SaaS。

## 4. 租戶識別 precedence(防跨租戶洩漏)

**絕不信路由層。** 解析順序 + 強制授權檢查:
1. **從請求解出候選租戶**|自訂網域(hostname 精確比對)→ subdomain → path prefix。**這只是路由提示,非授權決定。**
2. **認證後,以驗證過的 JWT `tenant_id` claim 為真實來源**;gateway **剝除 client 送的 `X-Tenant-ID` header**。
3. **驗證「路由候選 == JWT tenant_id」**,不符 → 拒。**從 host/path/header 推租戶而非驗證 token = 經典跨租戶洩漏破口。**
- **最佳實踐**|一個不可變 `tenant_id` claim(`sub` 留給 user);角色 scope 到同 token 的 `tenant_id`(無全域跨租戶角色陣列 → 防橫向移動)。

## 5. auth + authz(見 docs/20 研究 Part A/B)

- **auth / org 管理 → Better Auth + org/SSO/SCIM plugins**(docs/11 已選,驗證足夠)|TS-native、in-process、多租戶 org + 成員 + 角色 + 邀請 + **per-org 企業 SSO**(scope 到 organizationId)。⚠️ SAML SP 較年輕,簽約前對真實 Entra/Okta 驗;pin 版本。**fallback**|Zitadel(多租戶原生但 AGPL + 無 SAML SP 消費)/ Keycloak(完整 SAML SP 但 JVM 重)。
- **三層授權(form/field/record)→ MVP 自建,先不上 Zanzibar**|RLS(租戶隔離)+ NestJS Guard(表單級)+ DTO/column masking(欄位級),**藏在單一 authz service 邊界後可換**。三層本質是 role×resource×attribute(ABAC),非關聯圖。**outgrow 時(跨租戶分享 / 巢狀階層 / 多服務共用 / 需可審計自助政策)→ Cerbos 優先**(stateless YAML + `PlanResources` 產 SQL filter,最貼 form/field/record);OpenFGA/SpiceDB 只在關聯圖授權成主導時。

## 6. 兩個關鍵決策的答案

| 決策 | 答案 |
|---|---|
| **Better Auth orgs 夠 vs 需全套 IdP?** | **Better Auth 夠**(in-process TS,無 JVM,含 per-org SSO/SCIM)。只有大企業要求聯合其既有 SAML IdP、或要 auth 當獨立服務給非 TS 系統(Edge/MES)、或要 IdP 級 admin UI 才上 Keycloak/Zitadel。 |
| **三層權限要 Zanzibar authz 引擎嗎?** | **MVP 不用**。RLS + Guard + mask 足夠;藏在 authz service 邊界後。真需要時 **Cerbos 優先**(非 OpenFGA/SpiceDB —— 那是關聯圖用)。 |

## 7. 推薦 layered stack(組裝)

1. **路由邊緣**|wildcard DNS `*.weyver.app` + wildcard TLS;**Caddy on-demand TLS** 給自訂白牌網域(`ask` endpoint 查租戶/網域 registry 閘控)。
2. **租戶解析**|middleware 由 host 解候選 → **驗證 == JWT `tenant_id`**;header 邊緣剝除。
3. **context 傳遞**|**nestjs-cls** 持 `tenant_id`;**@nestjs-cls/transactional**(Knex+Drizzle)每請求包交易。
4. **DB 隔離**|**shared schema + RLS + `FORCE ROW LEVEL SECURITY`**;app 角色無 `BYPASSRLS`、非表 owner;每交易首句 `SET LOCAL app.tenant_id`;`tenant_id` 前導複合索引。
5. **連線池**|**PgBouncer transaction mode**(因 context 為 `SET LOCAL` 交易範圍,安全)。
6. **背景工作**|`tenant_id` 進 BullMQ/DBOS payload;worker 重建 CLS + 重下 `SET LOCAL`。
7. **升級路徑**|企業租戶 → schema-per-tenant(用 Knex 動態層)/ db-per-tenant(資料落地)。

## 8. 實作鐵則(→ 已同步 AGENTS.md)

- **[P0]** 每查詢綁租戶 + **RLS `FORCE`**;**app DB 角色無 `BYPASSRLS`、非表 owner**。
- **[P0]** 租戶 context 用 **`SET LOCAL`(交易範圍)** 非 `SET`;相容 PgBouncer transaction mode。
- **[P0]** **背景工作把 `tenant_id` 塞 payload,worker 重建 CLS + 重下 SET LOCAL**(ALS 不跨 queue)。
- **[P0]** 租戶識別以 **JWT `tenant_id` 為準**,剝除 client header,驗證路由候選 == token;不符即拒。
- **[P1]** `tenant_id` 前導複合索引;`BYPASSRLS` 只給 migration 角色。
