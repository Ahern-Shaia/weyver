# Weyver 產品開發功能順序表

> **文件性質**|Dependency-first 之 build order 排序表。將 docs/04 v2.1 之 429 MVP 人月拆為 sprint-level 可交付 feature block,對齊 docs/07 v2.7 solo 時程 + docs/11 v5 OSS-only tech stack。
> **範圍**|Phase -1 Foundation → Phase 0 Ragic + ERP essentials(可上線收費)→ Phase 1 完整 MVP(429 人月)→ Phase 2 對標(~823 人月)。
> **對象**|solo dev(16-18 hr/day 全職 + Claude Code Opus 4.7);未來 8 人擴編 team 亦適用(加速度 4-5x)。
> **版本**|2026-07-16 **v1**(對齊 docs/04 v2.1 OSS-only + docs/11 v5 + docs/07 v2.7)

---

## 0. 排序原則(先讀,避免爭論)

### 0.1 三大原則

0. **★ 一切皆表單(架構主張,2026-07-17)**|**表單引擎是 substrate,不是模組之一**|ERP/MES/ISO 之單據 / 主檔 / 品檢 / 文件皆為引擎上的表單 app。故**表單引擎(動態 schema + 子表 + 公式 + 關聯 + 工作流 + 權限)是最先做、最不能妥協的平台投資**;之後 ERP/MES/ISO 大量復用它。深層計算(GL / MRP / 成本 / 估值)為引擎之上的計算層,隨各模組補上。
1. **Dependency-first**|上游 blocking module 先做|表單引擎 substrate blocks 90% 其他 module
2. **可上線交付**|Phase 0 之產出必須「一家 pilot 客戶可用」,不做半殘 feature
3. **收費驅動 backlog**|Phase 0 交付愈早,現金流愈早進來 → 之後 Phase 1 / Phase 2 資源就位

### 0.2 Solo dev vs Team 之差別

| 面向 | Solo(16-18 hr/day)| Team(8 人)|
|---|---|---|
| 並行度 | 1 stream(頂多 2 交錯) | 8 stream(依模組拆) |
| Bandwidth 產能 | ~2 人月-equiv / 月 | ~10-12 人月-equiv / 月(含 overhead) |
| Deep work 領域 | 一次 focus 1-2 個模組 | 可同時 8 模組 |
| Bottleneck | 開發者本人 | Communication + integration |
| **本排序表用途** | 逐項 sequential 執行 | 拆多條 parallel track(見 § 8)|

### 0.3 何時偏離順序表

- **Pilot 客戶硬 deadline**|17 家導入 pipeline 之上線 deadline 硬 conflict → 優先導入,Weyver R&D 暫停
- **Blocking bug**|上游 module 出現 architectural 問題 → 回頭 refactor 而非往下推
- **需求變更**|pilot 客戶 must-have feature 之前未預期 → 插隊,更新 backlog

| Item | 內容 | Deliverable |
|---|---|---|

**Gate F-2**|新用戶註冊 → 建 tenant → 建 workspace → 邀請第二個 user → 兩 user 各自看到 own tenant data,不能 leak
