### 🔴 `193` 的二次更正(2026-08-06,實作 B 之前)

**M0 第一版把 `193` 判成「未解」,那是誤讀。** 我只看了程式碼片段就下結論,
而那段 JS(`!user.isInGroup('SYSAdmin')` → INVALID)看起來像在擋 admin。
讀全文之後,**最後那句備註才是關鍵**:

> **若是問卷式使用者或佈告欄式使用者,可以直接透過進階權限設定來調整新增資料的權限。**

拆開來看:

1. 標題的「管理員」是 **doc/32 那張表裡的表單級存取層級「管理者」**,不是系統管理員
2. Ragic 的存取層級是**固定套餐** —— 管理者 = 看全部 + 新增 + 改全部,**減不掉其中一項**
3. **中間層級(問卷式 / 佈告欄式)反而可以用 UI 調** —— 所以缺的不是「權限」,
   是「**最高層級能不能減項**」
4. JS 裡的 `SYSAdmin` 是**被放行的那方**,不是被擋的

**而我方的模型本來就沒有這個問題。** `setFormActions` 是**絕對集**(OQ-ARI-2=A),
「view + edit 但沒有 create」直接就設得出來 —— 本專案 2026-08-06 對
`buildEffectivePermissions` 實跑驗證,`hasAction(form, "create")` 回 `false`。

🔴 **所以四條 KB 是「三條已解、一條真缺口」,不是我原本寫的兩兩對半。**
唯一的真缺口是 `253`(軟性驗證),而它已於 **C-6 A 出貨**。

⚠️ **教訓**:我在 M0 讀的是**程式碼片段**而不是全文,於是把「放行 SYSAdmin」
誤讀成「擋 admin」,又把它推論成「我方缺 admin deny」。
**同一天第六次同型** —— 看了一部分就下結論,而答案在沒看的那一部分。

### 🔴 裁定:**先不要做 ZEN 決策表**

| 判準 | 結論 |
|---|---|
| 上游列的四條依據 | **三條已解、一條(`253`)是真缺口** → 這一項的**論據基礎幾乎全空** |
| 現有能力 | `@weyver/rules` 的條件 + C-4 的動作,已覆蓋「條件 → 動作」這一類 |
| 成本 | 每平台 10MB 原生二進位;而 2026-08-03 才因為「不值得」把它移掉 |
| 真正缺的 | **只有軟性驗證**(`253`)—— 便宜、直接對應真實 KB 需求,已作為 **C-6 A 出貨** |

⚠️ **這不是說 ZEN 永遠不做。** 決策表真正發揮價值的形狀是
**「多條件 × 多輸出、行數會長到幾十列」的表格式規則** —— 例如 R2 的
稅率矩陣 / 定價階梯 / 核准路由。**那時候再裝回來仍然是一行的事**(引原文)。
在 R1 的四條依據只剩下一條、而那一條已用 20 行解掉之後,**現在做它就是為了做而做**。

⚠️ **不得宣稱**|「Ragic 沒有視覺化規則引擎」—— 它有**條件式格式**(我方已 parity)。
真正成立的說法是:**它的條件式格式涵蓋不到的那些,官方答案是貼 JavaScript**,
而那四篇 KB 就是逐字證據。

## §1 改為做的(不需 ZEN)

### ✅ A|軟性驗證:「警告但仍可儲存」(對應 `doc-kb/253`)—— **SHIPPED**

現有的條件式格式已有 `required`(硬性)與 `message`(純提示)兩種效果,
**中間那一格是空的**:條件成立時**顯示警告 + 要求確認,但允許存**。

落地:

| | |
|---|---|
| 效果 | 第六種 `kind: "warn"`,併入既有 `formatEffectSchema`(OQ-RE-2)|
| 求值 | `evaluateWarnings`(`@weyver/rules`,前後端共用)|
| 閘 | **伺服器擋第一次** → `409 NEEDS_CONFIRMATION`,**並回得出警告內容**(只回「儲存失敗」的話使用者不知道要確認什麼)|
| 放行 | 帶 `acknowledgeWarnings` 重送;**伺服器重算** —— 規則中途被改的話擋的是新的那組 |
| 🔴 稽核 | `action_audit` `outcome=warn_acknowledged` + 警告內容。**這是唯一的控制力** —— 它本來就不擋(官方逐字「仍允許儲存」),價值在事後答得出「誰在看過警告後仍然存了」|
| 效能 | **沒有任何 warn 規則就早退,連前值都不讀**(第一版無條件多讀一次 `getRecord`,等於每次更新都多付一趟查詢)|

⚠️ **它擋不住決心繞過的人**(client 大可每次都帶 `acknowledgeWarnings`)——
**那是設計如此**,原始需求逐字就是「顯示提醒但仍允許儲存」。

### ~~B|admin 也能被限制~~ 🔴 **不做,延到 R2 SoD**

原本要做「表單級 deny 覆寫,優先於任何授予(含 admin)」。**二次查證後撤回**:

- **`doc-kb/193` 已解**(見上)—— 它要的「最高層級減項」我方絕對集覆寫本來就做得到,
  **本項失去了它唯一的一手依據**
- 剩下的訴求是「**連系統管理員都能被限制**」,而那是 **SoD(職責分離)**,
  `docs/04` v2.7 已明列於 **E 段、排 R2**
- 現在做等於**在 R2 的設計之前先蓋一半**,而 SoD 的資料模型(衝突矩陣 /
  違規報表 / 特權存取覆核)遠比一組 deny flag 大 —— 先做小的那個,
  幾乎必然變成要拆掉重來的第二套

⚠️ **仍然成立的風險紀錄**(留給 R2 SoD 接手):
`EffectivePermissions` 對 admin 是 `return this.allActions` 全動作特判,
且 `buildEffectivePermissions` 在 `isAdmin` 時**直接早退**、連 form metadata 都不載入。
要讓 admin 可被限制,那個早退是第一個要拆的地方。
**而 deny 一旦存在就必須有 break-glass** —— 建議 deny 不得涵蓋 `design`,
否則會出現沒有任何人救得回來的租戶。
