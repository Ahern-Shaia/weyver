### 站二|自己的相依套件

`@nestjs/schedule` 的 `SchedulerRegistry` **支援動態註冊**
(`addCronJob` / `deleteCronJob` / `getCronJobs`,已讀 `.d.ts` 確認)。

**但裁定:不用它。**

動態註冊 = 排程狀態活在**單一 process 的記憶體**裡。後果:
多實例部署時每個實例都會註冊同一批 job → **重複執行**;租戶改時間要 reload;
process 重啟要重建。而 repo 既有的 14 個 cron 全部走
**「DB 表當佇列 + 固定 ticker + advisory lock」** —— 那個形狀天生解掉多實例與動態性:
**「哪些排程到期了」是一句 SQL,不是一份記憶體狀態。**

沿用它。多一套機制只會讓兩者的語意分岔(同 C-4 對 BullMQ / DBOS 的裁定)。

### 站三|競品(2026-08-06 查證)

🔴 **`docs/32` 把這一項記為「排程任務(per-tenant cron)」—— 那是誤解。**
Ragic 沒有「使用者自訂的任意排程任務」。[`doc/96` 排程管理](https://www.ragic.com/intl/zh-TW/doc/96)
逐字(本專案開本機鏡像原文覆核):

> 你可以針對以下功能設定**執行時間**的排程:**提醒**、**重寄逾期簽核通知信**、**資料封存**、
> **表單填寫提醒**、**定期從網址匯入**、**SQL 資料庫同步**、**每日執行的程式(Daily Workflow)**
> 及 **定期寄出報表**,預設是根據帳號設定中的預設排程執行時間。
> **請注意各功能本身的設定還是回到該功能對應的介面調整。**

> 設定一項功能的排程會**套用到資料庫所有該功能的執行時間**,以下圖的提醒為例,
> 系統就會**在該時區每天的 19:00** 檢查資料庫中所有的提醒功能,如果有符合條件的,就會自動依序寄出提醒。

> 若同一功能有多組排程(例如定期從網址匯入、表單填寫提醒),可**分別設定各自的執行時間**。

> 要立刻執行某項排程,可以直接點**馬上執行**。

**拆出四個設計事實**:

1. 它是**管理頁**不是排程引擎 —— 設的是「**何時**」,設定內容留在各功能自己的介面
2. **per-tenant 時區**(「在該時區每天的 19:00」)
3. 一項功能的排程**套用到該租戶所有該功能的實例**,不是逐筆設
4. 有 **「馬上執行」**

### 🔴 那「排任意邏輯」呢?—— Ragic 的答案是 **Daily Workflow,而那要寫 JavaScript**

上面清單裡的「**每日執行的程式(Daily Workflow)**」就是它的通用排程,
而 Daily Workflow 是 [JavaScript 工作流程引擎](https://www.ragic.com/intl/zh-TW/doc/29) 的一種階段
(`doc/125` 列出的六種之一)。**`docs/31` 的「五篇 KB 教人寫 JS 補」有一篇正是每日同步**
([`doc-kb/260`](https://www.ragic.com/intl/zh-TW/doc-kb/260) 「如果你希望每日自動針對特定表單的
所有資料同步連結與載入欄位,**可以考慮利用程式**」)。

**這與 C-4 是同一條縫**:Ragic 的無程式排程只涵蓋**內建功能**,
排任意邏輯要寫 JS。我方以 C-4 已有的**封閉 allowlist** 做定時觸發 = 不寫程式的確定性排程。

對照〈向上設計三條〉:

| 條件 | 是否成立 |
|---|---|
| ① 巨人明確停在那裡 | ✅ `doc/96` 的清單只有內建功能;通用排程是 Daily Workflow = 寫 JS(`doc-kb/260` 逐字)|
| ② 架構讓我們過得去 | ✅ C-4 的封閉 allowlist + 條件求值 + 執行紀錄**已經在**,定時只是加一個時機 |
| ③ 對「取代 ERP」有意義 | ✅ 「每月 1 號結轉」「每日盤點提醒」是 ERP 的日常,而它們必須確定性 |

⚠️ **Airtable / Teable 都有 `SCHEDULED` 觸發**(本專案 2026-08-06 於別的模組查證過:
Airtable 官方觸發清單含「At a scheduled time」;Teable 的 automation 觸發亦有)。
**故「定時觸發」本身不是差異化,確定性才是** —— 同 C-4 的結論。

## §1 範圍

**做**|
1. **排程管理頁**|租戶設定各背景功能的執行時間(在自己的時區)+ 「馬上執行」
2. **C-4 定時觸發**|`trigger_def` 加第三種時機:每日 / 每週 / 每月的指定時刻

**不做**|
- 任意 cron 運算式(`*/7 * * * *`)—— Ragic 沒有,而且它會讓「馬上執行」與稽核變得難解釋
- 分鐘級排程 —— 最小粒度為**小時**,對齊 Ragic 的「每天 19:00」語意
- 排程執行任意程式 —— 🚫 第一約束,那正是要向上的位置

## §2 待裁定(OQ)

### OQ-SCH-1|哪些背景功能開放給租戶設定時間?

**建議:只開放「租戶看得到後果」的那幾個**,基礎設施維持系統固定。

| 開放 | 理由 |
|---|---|
| 通知派送 / 提醒 | Ragic `doc/96` 第一項;「早上 8 點收到今日待辦」是使用者要的 |
| 回收桶到期清理 | 後果是資料真的消失,租戶該能決定在哪個時段 |
| 定時觸發(新)| 本模組的主體 |

| **不開放** | 理由 |
|---|---|
| `event-fanout` / `webhook-delivery` / `trigger-async` | 那是**投遞延遲**不是排程 —— 開放只會讓人把它調慢然後抱怨慢 |
| `security.purgeAudit` / `scan` / `usage` | 平台維運,租戶不該能調 |
| `pdf.expire` | 與保留期政策綁定,不是獨立旋鈕 |

### OQ-SCH-2|時區怎麼算?

**建議:`tenants.timezone` 為唯一真實來源,ticker 每小時跑一次。**
每小時 ticker 用 `now() AT TIME ZONE t.timezone` 判斷「這個租戶現在是不是設定的那個小時」。
⚠️ **不要在應用層算時區** —— PG 的 tz 資料庫會隨映像更新,應用層自己算會與 `record.service`
既有的日期分組**用兩套規則**,而那正是「兩份鏡射必然漂移」。

### OQ-SCH-3|「馬上執行」要不要限流?

**建議:要,而且要記 audit。** 它是使用者可觸發的重活(掃全表);
沒有限流的話一個按鈕連按十次就是十份全表掃描。

### OQ-SCH-4|定時觸發的動作集?

**建議:與 C-4 一致(`updateSelf` / `pushTo`),但兩者都走非同步。**
定時沒有「使用者正在等存檔」的語境,故同步側的理由不成立。
⚠️ 連鎖上限沿用 C-4 的 `root_event_id` 機制,**定時觸發自己就是源頭**。

### OQ-SCH-5|漏跑怎麼辦(process 停機跨過執行時刻)?

**建議:補跑一次,但只補最近一次。**
記 `last_run_at`,ticker 發現「該跑的時刻已過且 `last_run_at` 早於它」就補。
⚠️ **不要把積欠的每一次都補** —— 停機三天後一次跑出 72 份日報是災難。

### M1+M3 落地紀錄

| 決定 | 內容 |
|---|---|
| **到期判斷整段在 PG** | 一句 `WITH local AS (SELECT ... now() AT TIME ZONE t.timezone ...)` 同時算出當地的時 / 星期 / 幾號 / 月底。應用層自己算會與 `record.service` 既有的日期分組**用兩套規則** |
| 🔴 **身分:以建立者執行** | C-4 拒絕系統身分,而排程**沒有觸發者** —— 沿用 C-4「actor 為 null 記 `denied`」的話定時觸發永遠不會跑。故加 `trigger_def.created_by`,以他的身分執行(建觸發器需 `design` 權,不擴權)。⚠️ 建立者離職後那條會開始記 `denied` —— **可見的失敗,不是靜默的** |
| **語意:掃全表逐筆判條件** | 照 Ragic 提醒的模型(`doc/96` 逐字「檢查資料庫中**所有的**提醒功能」),不是「執行一次」|
| **逐筆走 `updateRecord`,不做批次 SQL** | 批次 UPDATE 快得多,但會繞過修改紀錄 / 搜尋索引 / 事件 / 遮罩檢查**四樣**,而繞過的東西要三個月後才有人發現 |
| **漏跑補一次** | 到期條件是 `l.h >= schedule_hour`(不是 `=`),而「只補最近一次」由 `last_run_at` 的**當地日期**比較自然給 —— 停機三天回來只跑一次,不會補 72 次 |
| **無論成敗都標 `last_run_at`** | 失敗還一直重試的話,一條設壞的定時觸發會每小時掃一次全表。失敗要靠執行紀錄被看見,不是靠重試 |
| 🔴 **每月只給 1–28 或 0=月底** | 2 月沒有 29–31 號。讓人選得到一個「有些月份不會發生」的日期,等於**賣一個會靜默漏跑的設定**。月結選 0,`date_trunc + interval` 算得出來 |
| **定時側只做 `updateSelf`** | `pushTo` 掃一次全表可能建出上千筆,且跨到別張表 —— 量級與授權兩個問題疊在一起,需獨立裁定。**在 zod 邊界就明確拒絕**,不讓人設一個永遠不會跑的東西 |
| **排程不進草稿** | 與 `enabled` 同理由:那是「什麼時候跑」不是「跑什麼」,改時間還要按發布是反直覺的 |

### M4 落地(設計器入口)

| 決定 | 內容 |
|---|---|
| **時機是第三個核取方塊,與前兩者可並存** | 「建立時標記 + 每天重掃一次」是合理組合 —— 補上建立當下條件還不成立、後來才成立的那些 |

### 🔴 上限的處理刻意與 Ragic 相反

單次掃描上限 **1000 筆**。⚠️ **這個數字沒有外部依據**(同 C-4 的 `MAX_ATTEMPTS`)——
Ragic 可比的是「相關表單公式重算 2000 筆」,但那算的是公式、我方跑的是動作,不能直接搬。

**但處理方式是有依據的對照**。官方逐字([`doc-kb/281`](https://www.ragic.com/intl/zh-TW/doc-kb/281)):

> 若需重算的資料超過系統限制,**所有相關表單資料都不會進行公式重算**

—— 超過上限**整批放棄**。我方**處理前 1000 筆,並在執行紀錄註明還有多少沒處理**。
做一半並說出來,比什麼都不做然後只在左下角跳一個訊息好。

### ✅ S1 的處置:不補跑,但說得出來

**行為刻意不改。** 「週一該寄的週報在週二寄出」未必是使用者要的 ——
遲到的報表可能**比沒有更糟**:收件人會以為那是週二的數字。

改的是**靜默**。新增 `missed` outcome:每輪 ticker 在跑完到期的那些**之後**,
找出「`COALESCE(last_run_at, created_at)` 超過一個完整週期 + 一天寬限」的,
各記一筆 `missed`,並**把 `last_run_at` 標成現在**。那一標同時做兩件事 ——
避免每小時重複記,以及讓下一次排定的時刻能正常觸發。

| 細節 | |
|---|---|
| **順序不能反** | 偵測必須在 `fire()` **之後**。先偵測的話,每一條當下該跑的都會先被記一筆 `missed` |
| **`missed` 是獨立 outcome 不是 `failed`** | 兩者的處置完全不同:失敗要去看錯誤,漏跑要去看**為什麼那段時間服務沒在跑** |
| **前端文案** | 「漏跑(服務當時沒在執行)」—— 不能只寫「未執行」,那讀起來像條件不符 |
| ⚠️ **代價誠實記** | **停用一個月後重新啟用也會記一筆 `missed`** —— 我方沒有記「什麼時候被停用的」。那一筆不算錯(那段期間確實有排定的時刻過去而沒跑),只是顯而易見 |

**殘留**|S4(超量無自動續跑)· S5(DST 未實測)·
**排程管理頁(M2)未起** —— 既有背景功能(通知派送 / 回收桶清理)的執行時間
