🔴 **這段逐字推翻了一個我原本要做的東西**:我預設「有歷史就要能單筆回復」,
而 Ragic **明文只給大量修改與匯入還原**,單筆修改**不提供還原**。
兩層結構:①**每一筆**都有修改紀錄可看 ②**只有批次操作**可還原。
理由不難推:單筆還原會與公式、連結載入、workflow 的重算互相打架 ——
官方那六條限制裡有三條在講這件事。

**推論**|本模組 P0 = **看得到**(單筆 + 全庫兩個入口),**不做單筆還原**。
批次還原是另一件事(需要「一次操作 = 一個批次 id」的地基),列 P1。

## 1. 範圍

### 1.1 做(P0)

1. **`record_revision` 表**:每次寫入記一列(誰 / 何時 / 哪張表 / 哪一筆 / 版本 / 動作 / **欄位差異**)
2. **寫在唯一咽喉**:`insertOne` / `updateOne` 內,與資料同一交易
3. **單筆檢視**:記錄頁看得到「誰把什麼改成什麼」
4. **遮罩**:看不到的欄位,其歷史也看不到

### 1.2 不做,並說明為什麼

| 不做 | 為什麼 |
|---|---|
| **單筆還原** | §0.3 逐字:Ragic 只給大量修改與匯入。單筆還原會與公式 / 連結載入 / workflow 重算打架 |
| 批次還原 | 需要「一次操作 = 一個批次 id」的地基(匯入 / bulkUpdate 目前不發批次 id),列 P1 |
| 全庫「資料修改紀錄」管理頁 | P0 先做單筆(那才是天天看的);管理頁列 P1,但**表結構已為它留好索引** |
| 資料庫設計變更頁 | `ddl_audit` 已有資料,缺的只是頁面 → 併入 P1 的管理頁 |
| 欄位級的「誰看得到哪段歷史」細分 | 沿用既有的欄位遮罩,不另立一套 |

## 2. 開放問題(OQ-RV-N)— ✅ 已裁定 2026-08-05

| # | 議題 | 選項 | 裁定 |
|---|---|---|---|
| **OQ-RV-1** ⭐⭐ | 寫在哪一層 | A. 每個公開方法各寫一次<br>B. **`insertOne` / `updateOne` 兩支私有咽喉**<br>C. DB 觸發器 | **B** —— 這一輪已經數過:寫入路徑有建立 / 匯入 / 更新 / 貼上 / 主檔明細 / 還原六條,而**橫切關注點掛在單筆路徑上就會被繞過**(索引漏三次、事件漏兩次)。咽喉只有兩支,掛在那裡任何路徑都繞不過。C 看不到欄位顯示名(§0.2) |
| **OQ-RV-2** ⭐ | 存快照還是差異 | A. **只存差異**(改了哪些欄、前後值)<br>B. 整筆快照<br>C. 兩者都存 | **A** —— Ragic 逐字「列出該筆資料**詳細的修改內容**」= 差異視圖。B 的成本隨欄數與筆數相乘,而一張 100 欄的表改一個欄位要存 100 個值。**代價誠實**:不能直接還原到某個版本 —— 而 §0.3 說 Ragic 本來就不給單筆還原,代價與 parity 對齊 |
| **OQ-RV-3** ⭐ | 建立時要不要記全部欄位 | A. **記(視為「從無到有」)**<br>B. 只記一列「已建立」 | **A** —— 「這筆單子一開始長什麼樣」是查帳時的第一個問題。成本可接受:每筆記錄一生只有一次 |
| **OQ-RV-4** ⭐⭐ | 歷史值的權限 | A. 有記錄檢視權就看得到全部歷史<br>B. **逐欄套用既有欄位遮罩**<br>C. 歷史另立一套權限 | **B** —— 隱藏欄的歷史值就是隱藏欄的值。**這是本輪修過三次的同一個形狀**(公式污染閉包 / 連結標題 / 通知內容):值有第二個出口就會漏。C 是第二份權限來源,必然分岔 |
| **OQ-RV-5** | 保留期 | A. 永久<br>B. **與回收桶一致的可設定保留期**<br>C. 固定 N 天 | **B 的形狀,但 P0 先永久不刪** —— 表結構帶 `created_at` 索引,清理排程列 P1。⚠️ 誠實記:**這會長大**,一張高頻表一年可以到數百萬列。P1 必須做,不是可選 |
| **OQ-RV-6** | 值怎麼存 | A. 存**顯示值字串**<br>B. **存原始值 jsonb** | **B** —— 顯示格式會變(日期格式、選項改名、金額幣別),存顯示值等於把當時的格式凍進歷史,日後改設定就對不起來。讀時再用**當下的**欄位設定格式化 |

## 3. 資料模型

```
record_revision (Tier-1 系統表,**開 RLS FORCE**,只增不改;app 車道只給 SELECT / INSERT)
  id           bigint PK
  tenant_id    bigint NOT NULL          -- app 層綁定 + 查詢一律帶
  form_id      bigint NOT NULL
  record_id    bigint NOT NULL
  version      integer NOT NULL         -- 動態表的 version 欄(更新後的值)
  action       text NOT NULL            -- create | update
  actor_id     bigint NULL              -- 系統動作可為 null
  changes      jsonb NOT NULL           -- [{ field, before, after }]
  created_at   timestamptz NOT NULL
  index (tenant_id, form_id, record_id, id DESC)   -- 單筆檢視
  index (tenant_id, created_at DESC)               -- P1 的全庫頁
```

`changes` 以**欄位顯示名**為鍵(與 `record.values` 同一種指涉,前端不必再查表);
欄位日後改名時歷史保留當時的名字 —— 那是對的:那次修改當時就叫那個名字。

### 4-bis 落地紀錄(2026-08-05)

`record_revision`(migration `0052`)+ 寫在 `insertOne` / `updateOne` 兩支咽喉 +
`listRevisions`(逐欄遮罩,沿用既有的公式污染閉包 helper)+ `GET :recordId/revisions` +
記錄頁「修改紀錄」區塊。api 1087 · web 228 · e2e 152 全綠。

**🔴 落地時的三個判斷,都記在程式碼裡**|

1. **`drizzle-kit generate` 產出的 migration 把全部表重建了** —— 本專案的 migration 是
   **手寫**的,meta 快照停在 `0030`。已丟棄生成檔改手寫。
   ⚠️ **教訓**:先看隔壁的 migration 長什麼樣,再決定用哪個工具。
2. **這張表開 RLS,與 `ddl_audit` / `action_audit` 不同** —— 那兩張存「誰做了什麼動作」,
   這張存**欄位值本身**。值就該受租戶隔離的硬執法,不是只靠 app 層記得帶 `tenant_id`。
   app 車道**只給 SELECT / INSERT**:修改紀錄能被改就不是修改紀錄了。
3. **前值來自 DB、後值來自 payload,同一個數字會有兩種寫法**
   (`numeric(19,4)` 回 `3.0000000000`,送進來的是 `10`)——
   畫面上「3.0000000000 → 10」看起來像壞掉。已在顯示層去掉尾隨零,
   但**刻意不套欄位格式**:歷史裡的欄位可能已改型別或被刪,硬套會把「當時的值」
   渲染成今天的樣子,那是另一種說謊。

## 5. FMEA(pre-mortem)

| # | 失效 | 嚴重度 | 緩解 |
|---|---|---|---|
| V1 | 某條寫入路徑沒留紀錄 → 查帳時「這筆沒人改過」是**錯的答案** | **P0** | 掛在咽喉(OQ-RV-1);**列舉所有路徑的測試**(照抄事件那條的形狀) |
| V2 | 隱藏欄的值從歷史漏出去 | **P0** | 逐欄套遮罩(OQ-RV-4);e2e 兩個 actor |
| V3 | 寫歷史失敗導致資料寫不進去 | P1 | **同一交易**是刻意的:歷史與資料要嘛都成立要嘛都不成立。查帳用途下「資料存了但沒紀錄」比「兩個都失敗」更糟 |
| V4 | 表無限長大 | P1 | 保留期清理列 P1(OQ-RV-5),**並在 doc 明記這不是可選項** |
| V5 | 大量匯入產生大量 revision 拖慢匯入 | P1 | 匯入走 `insertOne` 逐列 → 逐列一則。**與事件同一個取捨**:來源不記等於資料悄悄沒有歷史。若成本浮現,批次寫入而非不寫 |
| V6 | 值裡有大附件 / 長文 → jsonb 爆大 | P2 | 差異只存有變動的欄;附件欄存檔名不存內容(既有 `formatFieldValue` 已是這個形狀) |
