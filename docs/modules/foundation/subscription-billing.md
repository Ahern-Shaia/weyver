## 1. 核心主張:**分開「計費自動化」與「計費地基」**

這是本模組唯一重要的判斷,其餘都是它的推論。

### 1.1 可以延後的(**現在不要做**)

金流串接(綠界 / 藍新 / Stripe)· 帳單產生 · 發票開立 · 催繳 dunning · 自助升降級 · proration 換算 · 折扣碼 · 試用轉換漏斗分析。

**理由**|這些**全都是自足的後加模組**,不侵入既有程式碼,且 17 家客戶手工開帳單完全可行(docs/04 A7 已明確採此路)。現在做等於為不存在的規模建設施。

### 1.2 **不能**延後的(理由不同,要分開講)

| 要件 | 為什麼不能延 |
|---|---|
| **① 用量歷史** | **過去無法重建。** 沒有逐日記錄,日後(a) 無法驗證 docs/05 的定價假設是否成立、(b) 客戶爭議「我上個月沒那麼多人」無從查證、(c) 無法知道超額。這是**唯一一種「晚做就永久失去」的資料**,其餘都只是工。 |
| **② 租戶生命週期狀態** | 停權 / 試用到期要在 **`TenantGuard`** 攔 —— 那是**每一個請求**都會過的熱路徑。現在加一個 nullable 欄 + 一次查詢是零成本;日後在已上線系統的熱路徑動刀是另一回事。 |
| **③ entitlement 單一檢查點** | 若模組持續在**沒有任何 entitlement 縫**的前提下累積,日後要加方案分級,就得回頭逐模組改 —— **成本隨模組數線性成長**,而模組數正在快速增加。現在立一個 `EntitlementService`(P0 一律回 `true`)成本近乎零,但把呼叫點的位置固定下來了。 |

> **要點**|①②③ 的共同性質是「**成本會隨時間上升**」;§1.1 那些的成本**不隨時間變化**。這就是分界線。

## 2. 具體預留(最小改動,零行為變化)

### 2.1 `tenants` 加三欄(全 nullable / 有預設 → 零遷移風險)

| 欄 | 型別 | 用途 |
|---|---|---|
| `status` | text default `'active'` | `trial` / `active` / `past_due` / `suspended` / `cancelled` |
| `plan_code` | text nullable | `starter` / `pro` / `enterprise`;NULL = 不受方案管(現況) |
| `trial_ends_at` | timestamptz nullable | 試用到期 |

### 2.2 `tenant_usage_daily`(append-only)

以「日 × 租戶 × 指標」為粒度累積:計費使用者數 · 表單數 · 記錄數 · 儲存位元組 · API 呼叫數 · (日後)AI token。

**設計要點**|**append-only 不可改**(承 AGENTS「傳票不可變」精神 —— 用量是計費憑據);由每日 job 寫入(復用 F-6 `cleanup.service` 的 advisory lock 模式);**保留期長於任何帳務爭議窗口**。

### 2.3 `EntitlementService` —— 單一檢查點,**P0 一律放行**

```
canUse(tenantId, capability): Promise<boolean>   // P0: return true
seatLimit(tenantId): Promise<number | null>      // P0: null(不限)
```

**關鍵在於呼叫點就位,不在於它現在會不會擋。** 現在把「這個能力屬於哪個方案」這件事**有地方可寫**,日後填表即可。

### 2.4 `QuotaService` 接上 plan

現行 `quotaFor()` 已是 `tenants` 欄 → env 預設 的兩層 fallback。改為三層:**`tenants` 覆寫 → plan 預設 → env 預設**。這是既有程式碼的自然延伸,不是新設施。

### 2.5 `TenantGuard` 加停權檢查

`status ∈ {suspended, cancelled}` → 拒絕(唯讀例外見 OQ-SB-5)。P0 因所有租戶都是 `active`,行為完全不變。

## 4. 台灣在地考量(日後實作時的已知約束,現在只記錄)

- **自家開發票**|Weyver 賣給台灣公司必須開**電子發票**(B2B 三聯式)。注意:docs/04 模組 **O 是做給客戶用的 ERP 電子發票**,與「Weyver 自己對客戶開票」是**不同的租戶脈絡**,不要假設可直接複用。

- **Onboarding 一次性費**|NT$50–200K,屬**專案收入非訂閱**,帳務上要分開(影響 ARR 計算的正確性)。

## 12. 失效場景反思(FMEA)— pre-mortem 預列

| # | 場景 | 預定緩解 | Sev |
|---|---|---|---|
| B1 | **停權邏輯誤傷正常租戶**(status 預設值錯 / 判斷反向)→ 全客戶無法使用 | `status` 預設 `'active'`;停權檢查採**白名單式**(只有明確 `suspended`/`cancelled` 才擋)而非黑名單;測試斷言「NULL / 未知值一律放行」 | **P0** |
| B2 | entitlement 誤擋已付費客戶功能 | P0 一律回 `true`;日後填內容時,**未知能力碼預設放行**(fail-open)—— 計費是商業邊界不是安全邊界,**不可與 authz 的 deny-by-default 混用** | **P0** |
| B3 | 用量記錄跨租戶錯置 → 帳單算到別人頭上 | `tenant_usage_daily` 帶 `tenant_id` + RLS;每日 job 逐租戶獨立交易;測試斷言隔離 | **P0** |
| B4 | 用量 job 漏跑一天 → 該日永久空缺 | job 冪等(唯一鍵 `(tenant_id, date, metric)`)+ 可補算指定日期;**缺漏可觀測**(管理端顯示最後成功日) | P1 |
| B5 | 計費使用者定義變更 → 歷史數字語意不一致 | `tenant_usage_daily` 存**指標碼**而非單一數字,新定義用新指標碼並存,不改寫歷史(承「不可變」) | P1 |
| B6 | 停權後客戶無法取回資料 → 商業 / 法律爭議 | OQ-SB-5=A 唯讀;**但匯出功能目前 ⬜ 未起** → 停權功能實際啟用前,匯出必須先具備,否則 A 的承諾是空的 | P1 |
| B7 | 手工開帳單期間無用量佐證 → 收費爭議 | 本模組 M2 即開始採集,**早於**自動化計費上線,使切換時已有歷史 | P1 |
| B8 | 用量表無限成長 | 每日 × 租戶 × 指標,量極小(百家租戶 × 10 指標 × 365 ≈ 36 萬列/年),**不需清理**;明列以免日後誤加清理 job 砍掉計費憑據 | P2 |
