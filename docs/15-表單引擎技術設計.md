# Weyver 表單引擎 Substrate 技術設計

> **文件性質**|命門地基設計。表單引擎是 Weyver 的 substrate(平台底層)—— ERP / MES / ISO 全部建構其上(見 docs/04 A17、docs/11 v7 § 2)。**此設計在開發 Phase 0 Sprint P0-1 之前定案**,是 docs/13 之最大 risk gate。
> **配套**|docs/04(功能)+ docs/11(技術棧 v7,modular monolith)+ docs/10(Ragic 功能分析)+ docs/13(P0-1 order)+ **docs/16(Baserow/NocoDB/Teable 技術拆解 —— 本設計多項決策的實證依據)**。
> **技術前提**|TS 7 + NestJS + Fastify + **PostgreSQL 16** + Drizzle ORM;全 OSS。
> **版本**|2026-07-18 **v2**(經 docs/16 三家 OSS 實證校正:真實表方向確認;租戶改 C 共享 schema + tenant_id、D 降選配;ORM 雙軌 Drizzle+Knex;公式改 fork Teable MIT ANTLR)

---

## 0. 為什麼這是命門

一切皆表單 —— 採購單 / 銷貨單 / 工單 / BOM / 品檢 / ISO 文件 都是表單引擎上的 app。這意味著|

- **選錯儲存策略,整個平台重來**|表單引擎的資料模型是所有模組的地基。
- **三個需求彼此拉扯,是本設計的核心張力**|
  1. **Ragic 級彈性** —— 使用者可自建任意表單(動態 schema),不寫程式。
  2. **ERP 級計算** —— GL 過帳、MRP 展開、成本結轉、庫存估值、跨表聚合報表,需要**真實可查詢 / 可索引 / 可約束的欄位**與**原生 SQL join / aggregate**。
  3. **企業級多租戶** —— 各廠家資料隔離、可獨立備份 / 遷移。
- 純 EAV / 純 JSONB 能滿足 (1) 卻犧牲 (2);純固定 schema 滿足 (2) 卻犧牲 (1)。**本設計的答案是「兩層資料模型」**。

---

## 1. 核心決策|兩層資料模型(Two-Tier)

**關鍵洞見**|Weyver 的資料其實有兩種本質不同的來源,不該用同一種儲存硬套:

| | **Tier 1 · 系統模組實體** | **Tier 2 · 使用者自建表單** |
|---|---|---|
| 來源 | Weyver 預建(ERP/MES/ISO 核心)| 客戶自行拖拉建立(Ragic 式)|
| 例子 | 傳票 / 科目 / 庫存異動 / BOM / 工單 / 批號 | 客訴表 / 供應商評鑑 / 自訂檢查表 |
| schema | **固定、Weyver 控管、版本遷移** | **動態、租戶自訂、隨時增改欄位** |
| 儲存 | **真實固定資料表**(real columns + FK + index + constraint)| **動態表 / JSONB(見 § 2)** |
| 計算需求 | **高**(GL/MRP/成本/估值 原生 SQL)| 低(ad-hoc 資料,聚合為輔)|
| 客製 | 租戶可**加自訂欄位**(JSONB extension column)| 全客製 |

**統一之處**|兩層都透過**同一個表單引擎層**(grid / form / 子表 / 公式 / Link&Load / 權限 / 自動 API)呈現與操作 —— 使用者感受不到底層差異,兩者都「是表單」。這就是「Ragic 彈性 + ERP 計算」得以並存的關鍵:**ERP 實體是預先建模的真實表(計算快又正確),使用者表單是動態的(彈性),但共用同一 UX / API substrate。**

```
        ┌─────────────────────────────────────────────┐
        │   表單引擎 UX / API Substrate(統一層)        │
        │  grid · form · 子表 · 公式 · Link&Load ·      │
        │  三層權限 · 自動 REST/tRPC · 檢視(7 種)       │
        └──────────────┬───────────────┬──────────────┘
                       │               │
        ┌──────────────▼──────┐  ┌─────▼───────────────────┐
        │ Tier 1 系統模組實體  │  │ Tier 2 使用者自建表單    │
        │ 固定真實表 + JSONB   │  │ 動態(§2 策略)          │
        │ 擴充欄 · RLS         │  │ per-tenant              │
        │ ← ERP 計算層原生 SQL │  │                         │
        └─────────────────────┘  └─────────────────────────┘
```

## 2. Tier 2 動態 schema 儲存策略(方案評估)

使用者自建表單的儲存,是本設計最需要拍板的技術選擇。四個方案:

| 方案 | 說明 | 查詢 / 聚合 | 彈性 | 約束 / 索引 | 多租戶 | 結論 |
|---|---|---|---|---|---|---|
| **A · EAV** | entity-attribute-value 三欄存所有 | 🔴 差(需大量 self-join)| 🟢 高 | 🔴 弱 | 中 | Ragic 老路,ERP 計算會痛,**否** |
| **B · JSONB records** | 單一 `records` 表 + `tenant_id` + `form_id` + `data JSONB` | 🟡 中(GIN index + JSON operator)| 🟢 高 | 🟡 中 | 🟢 簡單 | 起步快,複雜聚合弱 |
| **C · 每表單真實表(runtime DDL)** | 每 (租戶,表單) = 真實 Postgres 表,DDL 動態建 / 改 | 🟢 佳(原生 SQL)| 🟢 高 | 🟢 強 | 需管理 | **Baserow / NocoDB 路線** |
| **D · schema-per-tenant + 真實表** | 每租戶一個 Postgres schema,表單 = schema 內真實表 | 🟢 佳 | 🟢 高 | 🟢 強 | 🟢 隔離最佳 | **企業級最適** |

**建議(2026-07-18 經 docs/16 三家實證修正)|C(真實表 + 共享 schema + tenant_id)為主,D(schema-per-tenant)降為選配**|

> **實證校正**|docs/16 拆解 Baserow / NocoDB / Teable 三家 —— **全部用「每使用者表 = 一張真實 Postgres 表」+ 共享 schema + row-level 租戶 scoping,沒有一家用 schema-per-tenant**。真實表方向是產業共識;租戶隔離走 row-level 而非 schema-per-tenant。

- **預設 C**|Tier 2 使用者表 = 真實表,建 / 改跑 runtime DDL(`CREATE / ALTER TABLE`);**共享 schema + `tenant_id` + RLS** 做租戶隔離。與三家一致、生態成熟、**跨租戶 migration 簡單**(單一 schema)。欄位極動態者落 **JSONB overflow 欄**避免 DDL churn。
- **D(schema-per-tenant)降為選配**|僅「大型 / 高隔離 / 需獨立備份還原」客戶升級用;知道代價(跨 N schema migration + `search_path` 管理)。作為共享 schema 表數失控時的 fallback。
- **ORM 雙軌(Teable pattern,照抄)**|**Drizzle / Prisma 只擁有固定表**(metadata + Tier 1 系統 ERP 實體)→ schema 乾淨可 migrate;**動態 Tier 2 使用者表走 Knex / Kysely / raw SQL 平行車道**,由 metadata catalog 驅動,永不進 ORM schema。這直接解「ORM 需要靜態 schema」的難題。
- **欄位雙軸模型(Teable/NocoDB pattern)**|`cellValueType`(語意)vs `dbFieldType`(物理,含 JSONB)+ **visitor** 產生 DDL/SQL,型別邏輯與 SQL 生成解耦。
- **起步務實**|三家已證真實表可行,**直接做 C**,不需先繞 JSONB;metadata 層(§ 3)仍抽象化底層,日後可升 D。

> **Tier 1 系統實體**|一律**固定真實表 + 共享 schema + `tenant_id` + RLS**(結構跨租戶一致,不需 per-tenant schema);租戶自訂欄落該表的 `ext JSONB` 欄。ERP 計算層直接對這些原生欄位做 SQL。

## 3. Metadata 層(引擎的大腦)

不論 Tier 1/2、不論儲存策略,引擎由一組**中繼資料表**驅動(這些是 Weyver 系統表,固定 schema):

| Metadata 表 | 內容 |
|---|---|
| `form_def` | 表單定義(id / tenant / 名稱 / 資料夾 / 儲存策略 / 版本)|
| `field_def` | 欄位定義(表單 / 欄名 / 型別 / 驗證 / 預設 / 是否公式 / 是否關聯 / UI 設定)|
| `subform_def` | 子表定義(父表單 / 子表單 / 綁定關係)|
| `relation_def` | Link & Load 關聯(來源欄 / 目標表單 / 載入欄映射)|
| `formula_def` | 公式(欄位 / 運算式 / 依賴欄 / 觸發時機)|
| `view_def` | 檢視(表格 / 看板 / 日曆 / 圖表 / 表單…篩選 / 排序 / 分組 / 欄寬)|
| `workflow_def` | 工作流(狀態機 / 觸發 / 動作 / 簽核路徑)|
| `permission_def` | 三層權限規則(表單 / 欄位 / 記錄)|

**引擎啟動 / 表單載入時讀 metadata → 生成:DB 存取層、驗證、UI schema、REST/tRPC 契約、權限 filter。** 改表單 = 改 metadata(+ 必要時 DDL),不改引擎程式。

## 4. 欄位型別系統(30+ 型別 → Postgres 映射)

| 型別群 | 範例 | Tier 1 真實欄 | Tier 2(D)真實欄 |
|---|---|---|---|
| 文字 | 單行 / 多行 / Email / URL / 電話 | `text` / `citext` | 同 |
| 數值 | 整數 / 小數 / 金額 / 百分比 | `numeric` / `int8` | 同 |
| 日期 | 日期 / 日期時間 / 期間 | `date` / `timestamptz` | 同 |
| 選項 | 單選 / 多選 / 標籤 | `text` / `text[]` / enum | 同 |
| 自動編號 | `PO-YYYYMMDD-###` pattern | `text`(sequence 產生)| 同 |
| 布林 / 評分 | 勾選 / 星等 | `bool` / `int2` | 同 |
| 關聯 | Link & Load reference | `int8` FK + 快取欄 | 同 |
| 成員 / 部門 | user / org reference | `int8` FK | 同 |
| 檔案 / 圖片 | 附件 | `jsonb`(S3 key 陣列)| 同 |
| 公式 | 計算欄 | `generated` or 觸發維護 | 同 |
| 子表 | line items | 子表(FK 反向)| 同 |

- 每型別 = {Postgres 型別 + 驗證器(Zod / class-validator)+ UI 元件 + 格式化 + 篩選運算子}的一組定義,集中註冊。
- **自動編號**|用 Postgres sequence + pattern 格式化,交易內取號避免跳號 / 重號。

## 5. 子表(Subtable / Line Items)引擎

- **模型**|父表單(header)一列 ⇄ 子表單(line）多列,子表為獨立表 + `parent_id` FK + `line_no`。
- **聚合**|父欄公式 `= SUM(子表.小計)` 由公式引擎維護(§ 6)。
- **交易**|header + lines 存 / 改 / 刪在**單一 DB transaction**(原子);ERP 單據(採購單 / 傳票)剛需。
- 這是 ERP 單據的骨架 —— 採購單、傳票(借貸多行)、BOM(多階組件)、工單(領料明細)全靠它。

---

## 6. 公式引擎

- **引擎(2026-07-18 經 docs/16 修正)**|**優先 fork Teable `packages/formula`(MIT,ANTLR4 自訂文法)** —— 授權乾淨、已含 AST + 依賴圖 + 循環偵測 + 編譯成 dialect SQL,**省數月**。備選 HyperFormula(GPL/商用雙授權,授權疑慮)或自研 subset。Baserow / Teable 皆用 ANTLR 文法路線,NocoDB 用 jsep,**ANTLR 為主流**。
- **依賴圖**|`formula_def` 記錄每公式欄依賴哪些欄 → 建 DAG;某欄變更 → 拓撲序 recalc 下游,偵測循環依賴。
- **求值位置**|
  - **前端即時**|使用者填單時 client-side 算,給即時回饋(HyperFormula 同引擎跑瀏覽器)。
  - **後端權威**|存檔時 server-side 重算(權威值,防前端竄改);跨表 / 聚合 / 關聯公式**僅後端**。
- **物化**|公式結果落實體欄(讀快),透過觸發 / 存檔流程維護;不用 Postgres `GENERATED` 因跨表 / 函數受限。

---

## 7. 關聯 Link & Load

- **Link**|欄位指向另一表單的記錄(FK,`relation_def`)。
- **Load**|選定關聯記錄後,自動帶入來源表單多個欄位(如選供應商 → 帶統編 / 聯絡人 / 付款條件)。
- **實作**|載入欄可 (a) **快取**(存當下值,存量報表穩定、來源變動不追溯)或 (b) **即時**(join 查最新)。ERP 單據多採 (a)(單據應凍結交易當下的供應商資訊)。
- **參照完整性**|FK constraint(Tier 1)+ 應用層檢查;刪除來源記錄的 on-delete 策略依欄位設定。

---

## 8. 工作流引擎

- **狀態機**|`workflow_def` 定義狀態(草稿 / 待審 / 核准 / 退回…)+ 轉移規則 + 守衛條件。
- **觸發**|欄位變更 / 狀態轉移 / 排程 / 外部事件 → 動作(通知、寫他表、呼叫計算層、拋轉)。
- **簽核**|多關卡簽核路徑(依部門 / 角色 / 金額條件路由);對應 docs/04 C 單據流編排。
- **實作**|NestJS EventEmitter + BullMQ(非同步動作)+ 狀態轉移寫 audit log。
- **跨模組拋轉**|「採購核准 → 產生應付」在**單體內即一次 DB transaction**(呼應 docs/11 § 1.3 不拆微服務的理由)。

## 9. 三層權限模型

| 層級 | 粒度 | 實作 |
|---|---|---|
| **表單級** | 誰能看 / 建 / 改 / 刪某表單 | NestJS Guard + `permission_def` |
| **欄位級** | 某角色看不到 / 不能改某欄(如業務看不到成本欄)| 查詢時 column projection + 寫入時 mask;UI 隱藏 |
| **記錄級** | 只能看自己 / 部門 / 特定條件的記錄 | **Postgres RLS**(Tier 1)+ 應用層 filter(Tier 2)+ row owner / share list |

- **租戶隔離**|最外層 —— Tier 1 靠 `tenant_id` + RLS;Tier 2(D)靠 schema 隔離。**任何查詢一律先綁租戶**。
- 對應 docs/14 設計規則之權限,對應 docs/04 E 模組。

## 10. 計算層介面(ERP compute 如何掛上引擎)

ERP 深層計算(GL 過帳期結 / MRP / 成本 / 估值)= 引擎之上的 **NestJS services**,透過三種方式與表單引擎互動:

1. **讀**|直接對 Tier 1 真實表做原生 SQL(join / aggregate / window)—— 這正是選真實表而非 EAV/JSONB 的理由。
2. **寫**|計算結果透過引擎的 record API 寫回(產生傳票、更新庫存、寫成本),沿用同一驗證 / 權限 / audit / 工作流。
3. **掛勾**|訂閱工作流事件(§ 8),如「收貨確認 → 觸發庫存異動 service → 更新加權平均成本」。

> **原則**|計算層**不繞過**表單引擎直接改資料(除非效能熱點),以保持 audit / 權限 / 公式一致。熱點(如大量 MRP 展開)可走批次 service + 事後 recalc。

## 11. 每表單自動 API

- 由 metadata 生成 **REST(`@nestjs/swagger` OpenAPI）+ tRPC** 契約:list / get / create / update / delete / bulk。
- 自動套用:欄位驗證、三層權限 filter、工作流守衛、公式重算、audit。
- 對應 docs/04 G 模組(每張表單自動生成 REST API,Ragic 招牌)。

## 12. Phase 0 P0-1 風險與 Spike 計畫

**這是 docs/13 最大 risk gate。開發前先做 spike 驗證,別直接全做。**

| 風險 | Spike 驗證(建議 1-2 週先行) |
|---|---|
| 動態 DDL(方案 D)在多租戶下的鎖 / 遷移複雜度 | 建 10 tenant schema × 各 20 表,跑並發建表 / 改欄 / 查詢,量 DDL 鎖與 catalog 膨脹 |
| ERP 級查詢在動態表上的效能 | 對真實表跑 GL 餘額 / 庫存聚合 / 多表 join,對照 JSONB 方案,確認差距 |
| 公式引擎跨表 / 聚合 / 依賴圖正確性 | HyperFormula 授權確認 + 跨表聚合 recalc 正確性 + 循環偵測 |
| 兩層模型的統一 API 抽象是否漏 | 用同一 grid / API 同時跑 Tier 1(傳票)+ Tier 2(自訂表),確認 UX 一致 |

**Gate 判準**|上述 spike 全過,才進 P0-1 正式開發;若方案 D 的 DDL / 遷移在多租戶下失控,**fallback 到 B(JSONB records)起步**(metadata 層讓上層無感),日後再演進。
