## 1. 為什麼它像產品而不像後台

**一句話:後台是「一組畫面」,它是「一個系統」。**

它把大量預算花在**不產生任何資料的東西**上 —— 麵包屑、記錄分頁器 `1/3`、租戶切換器、
`⌘K` keycap、版本戳記 `v1.4.1`、狀態列 pipeline、明細合計。
這些不是功能,是**系統在對你交代它自己的形狀**。
內部後台從不做這件事:它假設你知道自己在哪、為什麼在這裡。

### 六個可指認的機制

| # | 機制 | 具體值 | 為什麼這是分水嶺 |
|---|---|---|---|
| ① | **主要動作近黑,不是品牌藍** | `#18181B`,每頁**只有一顆**實心 | 品牌藍當主按鈕是 Bootstrap / Tailwind 後台模板的胎記;近黑 + 唯一實心是 Linear / Stripe 那一代的胎記 |
| ② | **單一強調色** | `#2563EB` 一個,負責連結 / 選取 / 焦點 / 進行中 | 後台感很大一部分來自**紅綠燈沙拉**(藍連結 + 綠儲存 + 橘警告 + 紅刪除)—— 那是 `.btn-success/.btn-warning/.btn-danger` 的遺產 |
| ③ | **階層靠字重與顏色,不靠尺寸** | 頁標 20 / 儲存格 14 = **1.43×**;**每列只有一欄粗體** | 後台愛用 2–2.8×(大標題 + 大留白)—— 那正是 C 版被否決的形狀 |
| ④ | **格線比外框淺** | `#F0F0F2` < `#E4E4E7` | 規則自稱「整份研究 CP 值最高的一條」。決定 15 欄 × 12000 列讀起來是**紋理**還是**牢籠** |
| ⑤ | **資料擁有顏色,不是 UI 擁有顏色** | 選項色由建表者選一次 → 流到表格 chip / 看板色條 / 群組標頭 | 後台是設計師替 UI 上色;產品是**使用者的資料自己帶著顏色走** |
| ⑥ | **狀態機優先於 CRUD** | 主按鈕永遠是「核准並出貨 / 送出審核 / 結案」,**絕不是「儲存」** | 後台的動詞是 CRUD,產品的動詞是業務流程 |

### 更底層的一條

**它承認自己會被用 8 小時。**
36px 列高 · 不截斷識別碼 · tabular-nums · 最後一列 Tab 自動新增列 ·
逾期用純紅相對時間不加徽章 —— 這些都是「你要在這裡工作一整天」的設計。
後台是給**偶爾來改個設定的人**用的。**那是兩種完全不同的成本結構。**

## 3. 🔴 一個未解的衝突:E 案 vs「資料擁有顏色」

2026-08-08 裁定的 **E 案(型別圖示分組上色)與 `DESIGN-RULES.md` 相衝**:

- **E 案**|欄位型別依分組上色(基本藍 / 數值松綠 / 選擇紫 / 聯絡青 / 關聯梅)
- **DESIGN-RULES**|`.ft{ color:#8E8E96 }` —— 欄位型別圖示**單一灰**;
  只有**檢視型別**才上色(表格藍 / 看板琥珀 / 圖庫粉 / 表單綠 / 日曆紫);
  而且明列「**資料擁有顏色,不是 UI 擁有顏色**」——
  分組色是**我定的**,不是使用者定的,屬於 UI 上色。

### 3.1 軸不是「圖示灰不灰」,是**顏色的預算花在哪一層**

| 層 | 顏色回答什麼 | 誰決定 | 案 1 規則 | 案 2 E(現況) | 案 3 全上 |
|---|---|---|:-:|:-:|:-:|
| **型別層** | 這欄是什麼**型別** | 設計師 | 灰 | **分組色** | 分組色 |
| **資料層** | 這一格的**值**是什麼 | **建表的使用者** | **選項色** | 灰 | 選項色 |
| **導覽層** | 這是哪種**檢視** | 設計師 | **檢視型別色** | 灰 | 檢視型別色 |

三層不能都上 —— 那是規則 §5 反面教材的「三個互相競爭的強調色」(isoTracker 的病)。
**案 3 是故意畫出來讓失敗看得見的,不是候選。**

對照稿 `docs/mockups/_color-ownership-compare.html`(截圖 `color-ownership-compare.png`),
全部真實尺寸、圖示由 node_modules 抽出。

### 3.2 🔴 查證翻掉了我原本的折衷案

我本來要在對照裡寫「案 1 的選項色要等 `option-colors` 模組做出來」——**那是錯的**。

**`docs/modules/R1/option-colors.md` 已 SHIPPED v1.0(2026-07-28)**:
`choices-editor.tsx` 讓**建表者逐選項挑顏色**,存成 `{id, name, color}`,
另有 `option-tone.ts` 做安全對映(含 CSS 注入測試)。
而當時 **OQ-OC-1 = B** 的裁定逐字記著決策方明示:
「**推翻 `docs/14 §0.1` 也沒關係,我要的是完整的解決方案**」。

→ **案 1 的資料層顏色不是示意圖,是已經出貨的真功能**;
   案 2 的型別分組色是我 2026-08-08 才自己定的,**沒有任何使用者輸入**。
   「資料擁有顏色」在這個 repo 裡**已經有實作,只是網格還沒把它畫出來**。

→ 原本的「折衷案 3」因此失效 —— 它的內容就是案 1,而且案 1 的前提已經成立。
   **實際只剩兩個選項:案 1 或案 2。**

⚠️ **仍待確認**:選項色**流到看板色條與群組標頭**那一段,
`option-colors §122` 當時記「尚無看板視圖與圖表模組」,而看板後來出貨了 —— **未複查是否已接上**。

### 4.1 步驟 1 落地紀錄(2026-08-08)

`--action:#1a2029` / `--action-h:#2c333e`,`.btn.pri` 由 `--brand` 改吃 `--action`。

**值不取規則的 `#18181B`,取決策方自己登入頁的 `oklch(24% .02 260)`** —— 換算 `#1a2029`,
略帶藍。同一個東西,但用決策方已經選過的那個,少一次無謂的分歧。
`--brand` 保留,職責收斂成**強調色**:連結 · 選取 · 焦點 · 進行中。

🔴 **順帶查了「每頁只有一顆實心」,而規則的字面意思是錯的**:
`s-form` 與 `s-norows` 各有兩顆。但**參考的 `grid.png` 自己就是兩顆**
(工具列「+ 新增訂單」+ 抽屜底「核准並出貨」)——
所以實際判準是**每個區域一顆**,不是每頁一顆。
→ `s-form` 不動(工具列 + 記錄抽屜是兩個不同區域的不同動作);
   `s-norows` 是真違反(工具列「建立記錄」與空狀態「建立第一筆」是**同一個動作**),
   已把工具列那顆降為次要 —— 空狀態擁有這個畫面的 CTA。

**觀察**|近黑主按鈕讓 accent 藍退回它該在的位置(連結與選取),
而不是同時當「品牌色」與「主要動作」兩個角色。這是六機制裡 ① 與 ② 連動的效果 ——
單獨改一個看不出來。

⚠️ **登入頁不動** —— 那是決策方自己的設計,它的 `登 入` 是高彩度藍、`註 冊` 是近黑外框,
本來就是成對的。改它等於覆寫決策方的作品。

### 4.2 步驟 2 落地紀錄(2026-08-08)

**G7 列高 31 → 36px、內距 8 → 10px。**
`DESIGN-RULES.md` §2.3:「三家獨立量測收斂:32–36px 列高、8–12px 儲存格內距」,
並明列「列高不要膨脹到 52px」。
🔴 **我原本 31px 是偏低的那一邊** —— 密度不是越高越好,36px 是三家收斂出來的位置。

**G4 每列只有一欄粗體。**
🔴 **改之前每列有兩個粗體** —— 識別欄不是粗的,而**計算欄(金額 / 含稅金額)是**。
那正好顛倒:規則說那一個粗體應該是**識別欄**(你用它找記錄),不是算出來的值。
→ `.g tbody .frz{font-weight:600}`、`.g td.ro` 取消 `font-weight:600`。
計算欄的區辨已由「唯讀灰填色 + fx 色」承擔,不需要再加字重。

**量測驗收**(Playwright,非目測)|列高 **36px** · 內距 **10px** ·
**每列粗體欄數 1**,且是 `PO-2026-0847`。

### 4.3 步驟 3 落地紀錄(2026-08-08)

**G2 麵包屑 —— 關鍵在它「取代」大標題,不是加在上面。**
參考的 `grid.png` 是 `訂單管理 / 銷售訂單 / 全部訂單`,**最後一段就是當前檢視名,
沒有另外的 H1**。這順了 §2.2「階層靠字重與顏色,不靠尺寸」:
末段 600 + 前段 400 灰,一行把層級講完,而且**比 15px 標題少一條視覺軸**。
→ 三個畫面都上:`s-form`(三段,末段是檢視名)· `s-norows` · `s-design`(兩段)。
⚠️ **清單檢視用麵包屑、記錄檢視才用大標題**(record-title 24/600)——
兩者不衝突,是不同物件。

**G3 記錄分頁器。** `DESIGN-RULES.md` §3.3 逐字:
「記錄分頁器放頂列(`4 / 24` 配 `‹ ›`)。可以走訪篩選結果集而不用回列表。
**企業工具常常忘記這個。**」
⚠️ **我方放在記錄面板的標題列而非全域頂列** —— 記錄在我們這裡是右側面板,
分頁器屬於「這個面板正在看第幾筆」;放全域頂列會和「這張表有幾筆」混淆。
這是對規則位置的**刻意偏離**,理由記在此。

### 4.4 步驟 4 落地紀錄(2026-08-08)

**G6 側欄 206 → 260px。** §2.3 明列 260px;§1 的理由是把 Ragic 疊的四層導覽
(吃掉 118px 垂直 + 306px 水平)壓成**單一側欄承載群組 / 樹 / 檢視** ——
206px 撐不住三層縮排。

**G5 租戶切換器釘在側欄最上。** §3.6:「頂:租戶切換器(多租戶從第一天就有,Ragic 做對了)」。
🔴 **它同時修掉一個既有的混淆**:原本頂欄的 `whoami` 把**使用者與租戶擠在一起**
(陳品妤 / 鮮勇食品)—— 那是兩個不同的東西,切換的對象也不同。
→ 側欄頂 = **租戶**(可切換)· 頂欄右 = **使用者**帳號 · 側欄底 = 版本戳記(去掉重複的使用者名)。

⚠️ **量測時我的檢查給了偽陰性**:三個 `.ctx` 量到 `[260, 0, 0]`,
`單一寬度:false` —— 但那兩個 0 是**隱藏畫面**的 `.ctx`(父層 `hidden`)。
改用「`.ctx{width:` 規則數 = 1」確認才是對的判準。
又一次「代理指標的輸出不是答案」—— 差點把偽陰性報成缺陷。

#### 4.4-bis 🔴 G6 漏掃了設計器頁(2026-08-08 由決策方指出)

G6 只改到 `.ctx`,**設計器頁的左軌沒跟上**。而量下去發現不只是寬度:

| 頁 | 左軌 |
|---|---|
| 表單工作面 / 範本庫 / 空·表單 | `.ctx` **260px** —— 租戶 → 群組 → 表單清單 → 檢視樹 |
| **表單設計** | `.fd-pal` **186px**,而且 **`.ctx` 整條不見** |

**所以真正的問題不是寬度沒同步,是設計模式把第二層導覽整個丟掉了。**

裁定|**同一條軌換內容,寬度沿用 260** —— 不加第二條軌。
- Ragic 官方逐字:「在**設計模式**下,**左側面板**的『基本』下可以看到欄位種類」
  → 設計模式是**換左側面板的內容**,不是多加一條。
- ⚠️ 我方**產品**的殼是 196px 導覽 + 178px 元件庫**兩條**(`app/layout.tsx:255`),

  再加一條等於憑空多出第三層。
- 軌換了內容就要講出來,否則使用者會以為表單樹不見了 → 加軌頭「加入到這張表 · 採購單」。

量測|軌 260px(與 `.ctx` 同)· 主體佔比 **69.3%**(S4 要 ≥60%)· 畫布紙張 860px 不變。

**教訓**|這正是 [[rule_outer_shell_sweep]] 說的那件事:
**cross-cutting 的版面改動要把所有畫面一起掃**,不能只掃「看起來相關」的那幾頁。

### 4.5 步驟 5 落地紀錄(2026-08-08)

**不要**畫沒有 CTA 的裝飾性空狀態(Metabase 的問題)。」

### 4.6 步驟 6 落地紀錄(2026-08-08)—— 字體三分工

決策方裁定採建議:**Archivo 只給品牌與大標,內文 Inter + Noto Sans TC,等寬 IBM Plex Mono**。

| token | 值 | 給誰 |
|---|---|---|
| `--font-display` | `'Archivo','Noto Sans TC'` | 品牌字樣 + 5 個大標 |
| `--font-sans` | `'Inter','Noto Sans TC',…` | 內文 / UI / 資料 |
| `--font-mono` | `'IBM Plex Mono'` | **只給機器識別碼**(§2.2)。規則寫 JetBrains Mono,取決策方登入頁已選的那個 |

⚠️ **物理事實**:**Archivo 沒有 CJK 字符**,中文一定 fallback 到 Noto Sans TC ——
所以「大標用 Archivo」實際只影響**拉丁字與數字**。
那正是登入頁「不用寫 **code** 的表單資料庫」的效果:同一行兩種字身。

**🔴 換字體的代價當場出現了,如預期**|

記錄面板子表的「真空包裝袋 25×35」**由一行變兩行**(該格 44px)。
這正是把 G8 排在最後的原因 —— 若先換字體,前五步每一步都要重量一次。

**🟡 順帶暴露一個未列的落差**:`DESIGN-RULES.md` §2.2 明列

### 6.1 補完功能面時,S5 逼出一個更好的解

提案稿原本只畫了約 **1/3 的功能面**。補的時候撞到 `docs/29` **S5「水平 header 帶 ≤ 1 條」**
—— 產品的六顆版面工具(文字/圖片/分段/動作·簽核/列印/條件式格式)自己佔一條帶,
提案稿不能為它們再開一條。

**解法不是塞進同一條,是重新分類**:

- **文字 / 圖片 / 分段 → 移進元件庫**,獨立「版面」群、**不吃分組色**(它們不是欄位型別,沒有「值的形狀」可指)。
  依據是 **task #154 自己的原則,逐字**:「加欄位與加子表都是**往這張表加東西**,
  所以該在同一個地方、長同一個樣子」—— 版面元素是同一個動作類別。
- **動作·簽核 / 條件式格式 / 列印 → 留在唯一那條帶上**,因為它們是**表單級設定**不是「加東西」。
  三者與欄位設定**共用右欄且互斥**(照產品的 `toggleAux`,再點一次收合)。

量測:工具列 1452px **無溢出**;右欄恆為一欄。

### 6.2 往上設計第一站:拋轉對映

選這裡不是因為它顯眼,是因為**「不用寫程式」的風險最集中在自動化那一段**。
現況四個限制,每一條都把使用者推向 API:

| 現況 | 為什麼是第一約束風險 |
|---|---|
| **一個按鈕只能對映一個欄位**(`actions.tsx` 的 `fieldMap` 只塞單一鍵) | 真實單據的拋轉一次要帶五六欄 → 只能改打 API |
| **只有新增與刪除,沒有編輯** | 改一個字要刪掉重建 |
| **目標欄名是手打字串**,不是下拉 | 打錯不會有人告訴你,而對照表就在系統裡 |
| 清單直接顯示 `updateSelf` / `pushTo` | 同一面板其他地方全中文,只有這裡漏出內部值 |

提案稿的「動作 · 簽核 → 自訂按鈕」四條全解:多欄對映(`＋ 再加一組`)· 每列有「編輯」·
來源與目標**兩側都用選的** · 清單顯示「拋轉到其他表單 · 2 欄」。

**未做**|加欄卡刻意不畫 —— 它是 `OQ-FDW-3=B′`(Enter 即建欄 + 表尾 ghost row)**要取代掉的東西**,
畫進提案稿會自相矛盾。列印與靜態元素設定面板只在凍結稿裡有。
