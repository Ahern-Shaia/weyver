v0.4 改動:四個獨立勾選框 → 單一有序層級|原稿抄 Ragic 的 4 個布林開關,但 GitHub / GitLab / Discourse / Zulip / Notion / Slack / Teams / Linear 無一例外用單一 enum,且查不到任何系統從 enum 退回獨立開關。4 個開關 = 16 種組合,其中「勾新增、不勾與我相關」= 別人建的通知、自己建的不通知 —— 沒人想要卻可表達。
「與我相關」是地板,不是開關|它現在是預設層級而非第一個 checkbox。GitHub 明載取消 watch 後「仍會收到你參與的對話」,只有 Ignore 全靜音。要完全不收自己建立的資料,得刻意選「靜音」。
三軸分離|軸 0 總開關 · 軸 1 層級(收多少)· 軸 2 通道(從哪收)。v0.3 把「收多少」和「與我相關」混在同一排開關裡,是維度錯置。
層級沿用既有的分類資源軸|全域 → 分類 → 表單,未設定則繼承上層,最具體者勝(GitLab 語意)。這與已 SHIPPED 的權限資源軸繼承是同一條軸,使用者不必學第二套心智模型。Discourse 的教訓:多維度繼承未寫進文件 = 永久客服,所以繼承規則要明文。
P0 只有 5 檔,不是研究建議的 6 檔|建議中的「只有被提及」需要 @提及,而 Weyver 尚無註解功能 —— 不做無法運作的檔位,與「不做假開關」同一原則。

信裡同樣沒有金額、品項、供應商 —— 與站內通知同一條規則(OQ-NT-9)。Email 會離開系統、可能被轉寄、留在收件匣,把受權限保護的欄位值放進去風險更高。
有的只是「誰、什麼時候、哪一筆」|這三項來自記錄本身的系統欄,不是使用者自訂欄位,不受欄位級權限影響。
退訂連結是必要的,不只是禮貌 —— 沒有它容易被判為垃圾信,影響整個寄件網域的信譽(FMEA N8)。
待確認|寄件者顯示「鮮勇食品」(租戶名)但網域是平台的。P0 用平台級 SMTP,租戶自訂寄件網域(需 SPF/DKIM 驗證)為後續。
7通知風暴防護 — 使用者看得到的部分承 Ragic

批次匯入不會發送逐筆通知。
Ragic 明載「透過大量修改或匯入的資料即使符合條件也不會寄送通知」 —— 這是刻意的防護不是遺漏。UI 上要講出來,否則使用者會以為通知壞了。
這條規則也決定了架構:事件必須從 service 層顯式發出,不能用 DB trigger 或攔截所有寫入 —— 後兩者分不出批次與單筆(OQ-NT-3)。
8LINE 個人 vs 群組 — 兩種不同的功能非 P0,但模型現在就要對
個人 1:1通知訂閱
收件人|一位已驗證身分的使用者
誰決定收不收|使用者自己(三層設定)
權限|收件人的 —— 點進去時檢查
「跟我相關」|成立
身分怎麼來|本人驗證(加好友 → 傳信箱 → 收驗證信 → 點連結)
退訂|使用者自己關
審計|「已送達某人」
群組事件廣播
收件人|不特定多數人 —— 可能含非 Weyver 使用者、外部廠商
誰決定收不收|沒有訂閱者,由管理者設定
權限|無人的權限適用
「跟我相關」|無意義(群組不是「我」)
身分怎麼來|管理者邀 bot 進群 → 取得 groupId → 清單選定
退訂|只能管理者移除或踢出 bot
審計|「已廣播至某群組」—— 無法宣稱任何個人已知悉
所以群組設定不在個人設定裡|三層訂閱回答的是「我要不要收」,而使用者無法替一個群組決定訂閱。群組屬「表單設定 / 租戶通道設定」(管理者權限),歸 docs/04 已編列的通知路由引擎。
群組讓「通知不含欄位值」從偏好變成不可協商|個人通知至少收件人明確、點進去還有權限把關;群組廣播沒有任何權限模型可依靠。帶欄位值等於把資料推給一群系統從未驗證過的人。設定頁必須明示「群組內所有人都會看到」。
對 P0 的實際影響:收件人模型必須是多型的|若通知只記 recipient_user_id,群組通知根本無法表示。P0 不做群組,不代表模型可以不支援 —— 這正是「被 Email 形狀鎖死」的具體案例,M1 就要改對。
—本稿刻意不含(各有理由)
  • 提醒(日期驅動) —— Ragic 的「出貨日前三天提醒業務」需要每日掃全表的排程器,而 cron 排程整項未起。現在自建一次性 tick 會變成日後排程模組要拆掉的債。代價:Ragic 客戶熟悉的功能 P0 不可用。
  • LINE / Slack / Teams 等外部通道 —— 成本不在送訊息 API,而在綁定流程(需 inbound webhook + 驗證往返)、租戶憑證管理。大到應自成模組。抽象已預留,加通道不需重做。
  • 註解 / @提及 —— Weyver 尚無註解功能。它本身需要權限、通知、@解析,是獨立題目。
  • 摘要 / 合併 —— Ragic 的合併是「提醒」專屬行為(同表單同天多筆),而提醒不在 P0。事件型通知本來就該即時且獨立。
  • 手機推播 —— 無行動 App,無載體。
✓Review 裁定(2026-07-28)
  • LINE 欄 P0 不顯示 —— P0 既無 driver 也無連接設定頁,該列無法由任何操作變成「已連接」,是死控件。與「不做假開關」同一原則。
  • 「查看全部通知」P0 只做面板 + 最近 50 則,獨立頁後續。
  • 通知設定放個人設定底下。
  • 簽核逾期豁免總開關,一律發送 —— 流程無限期卡住的風險高於使用者意願。但必須在設定頁明白告知(步驟 4、5 已加告示),靜默的例外會讓使用者以為設定壞了。
Review 另揪出一個設計缺漏|決策方指出 LINE 有個人與群組之分,查證後確認 docs/04 §H 早已明載「個人 1:1 + 群組」且註明「台灣 SMB 日常 LINE 群組通知」,而 M0 v0.2 只設計了個人綁定。已補為 §4.6 + OQ-NT-13/14 + FMEA N12/N13(見步驟 8)。
