00

先修正:設計文件把目標搞錯了

實作前查程式碼的結果

  • line-items.tsx —— 設計文件原本指定的目標,但它是唯讀顯示表,儲存格是純文字、沒有 input。 APG grid 的核心(F2 切換編輯 / Enter 進編輯 / 英數直接輸入)在這裡無處可用。
  • builder/_components/records/form-panel.tsx —— 真正可編輯的子表在這裡, <table> 內每格是 FieldInput。這才是唯一適用 grid pattern 的面。
  • collection-view.tsx —— Glide canvas,自帶鍵盤,明確不動。
  • record-list.tsx —— 按鈕清單,屬 listbox 非 grid(不同規範)。
01

實際按按看 —— 可編輯子表

兩邊資料相同。先點左邊第一格,一路按 Tab;再點右邊,用方向鍵移動、F2 或 Enter 編輯。

現況 每格一個 input,靠 Tab 逐格移動

按完之後,請注意這幾件事

  • Tab 次數|左邊要走完 5 列 × 4 欄需按 20 次 Tab;右邊整個表格只有 1 個 Tab 停點,進出表格各 1 次。
  • 離開表格|左邊必須一路 Tab 到底才能離開;右邊按一次 Tab 就跳出去。(這是 FMEA U4 —— 做壞了會變鍵盤陷阱,屬 WCAG A 級違規)
  • 誤改風險|左邊每格恆為 input,方向鍵在輸入框內是移動游標,不小心打字就改到資料;右邊導覽態不吃輸入,要 F2 才進編輯。
  • 學習成本|右邊的鍵位與 Excel 幾乎相同(F2 / Ctrl+Home / Esc),目標客戶是 Excel 與 Ragic 重度使用者。
02

要不要做 —— 三個選項

選項得到什麼成本 / 風險
A 完整 APG grid
只做可編輯子表		 Tab 由 20 次降為 1 次;導覽/編輯分離避免誤改;鍵位對齊 Excel 肌肉記憶;符合 W3C 官方規範 roving tabindex 實作錯即成鍵盤陷阱(WCAG A 級違規);需逐鍵 e2e;與 FieldInput 15 種型別的互動需逐一驗(下拉/日期/附件各有自己的鍵盤行為)
B 只做最小集
方向鍵 + Esc,不做編輯態切換		 方向鍵可跨格移動,不必狂按 Tab 仍是「每格恆為 input」,誤改風險不變;半套的鍵盤反而更難預期
C 不做 零成本零風險;Tab 本來就能用(WCAG 2.1.1 鍵盤可操作性已滿足) 子表逐格 Tab 對每天填幾十列的使用者是持續成本;與 Ragic / Excel 慣例有落差

誠實的判斷依據

  • 不做不違反無障礙。 WCAG 2.1.1 只要求「可用鍵盤操作」,現況 Tab 可達即已滿足。APG grid pattern 是最佳實務,不是合規門檻。
  • 值不值得,取決於子表的實際使用量。 若 pilot 客戶的採購單/進貨單常態是 20–50 列明細,A 的回收很快;若多為 3–5 列,差異有限。這一點我沒有數據,需要你的領域判斷。
  • 風險集中在 U4。 roving tabindex 做錯會造成鍵盤陷阱,那比「要多按幾次 Tab」嚴重得多。做的話 e2e 必須逐鍵斷言可 Tab 出。
  • Glide 那一面不受影響 —— 集合視圖已自帶鍵盤,本案不動它。
