### 1.2 Claude Code 加速倍率的分項差異

| 類別 | multiplier | 說明 |
|---|---|---|
| Boilerplate UI / CRUD | 3–4x | Claude Code 強項 |
| 平台架構 / 多租戶 | 2x | 需慎重設計 |
| 業務邏輯(明確 spec) | 2.5x | |
| 合規邏輯(勞健保 / 電子發票) | **1.5x** | 卡點在 domain knowledge,非 code |
| 黑盒整合(鼎新 DB / SAP B1 SLD) | **1.3x** | debugging 為瓶頸 |
| Ops / 部署 / CI | 2.5x | |
| 客服 / bug fix / 生產環境排查 | 1–1.5x | hardware 對接與客戶溝通不受 AI 加速 |

**Weyver 專案 mix blended ≈ 2x**(整合密度高 + 合規要求高)。

### 1.3 Solo sustained pace(16-18 hr/day 全職 + Claude Code 2x)

**投入強度|全職 16–18 hr/day,週 6 日**(週約 96–108 hr,對照標準 FTE 40 hr/week 為 ~2.4–2.7x 原始 hours)。

分層產能推算|

| 層級 | 產能 | 計算 |
|---|---|---|
| 標準 FTE 產出基準 | 12 人月 / 年 | 8 hr/day × 5 day/week × 標準 sustained |
| 原始 hours 加乘(16-18 hr/day × 6 day/week) | ×2.4–2.7 | 對照標準 40 hr/week |
| 12+ hr/day 邊際效用遞減折損 | ×0.6–0.7 | 認知能力於長時工作後下降(產業研究) |
| **淨有效 hours 加乘** | **×1.4–1.6** | 對比標準 FTE 有效產能 |
| × Claude Code blended 2x | ×2 | mix blended(整合密度高 + 合規要求高) |
| **總產能上限** | **~34–38 人月-equivalent / 年** | 全職 100% Weyver 情境 |
| **本規劃採用值** | **~36 人月-equivalent / 年** | 保守中位 |

**本數值為全職 100% Weyver 情境上限**。實際 Weyver 產出需按階段扣除 17 家導入 pressure 佔用比例(見 § 2 場景 & § 4 phase 分佈)。

### 1.4 實證校準|Vernova AI 專案 commit 速度反推

**背景**|本開發者(ahern)於另一 SaaS 專案(Vernova AI,RAG + AI 平台)之 git 歷史,提供 Claude Code 輔助下之**實測個人產能基準**,用以校準 § 1.3 之 ~36 人月-equivalent / 年 假設。**該 repo 為多人共作,本校準僅計 ahern 本人之 commit,其餘協作者之 commit 全數剔除**(避免污染個人開發效率讀數)。以下數據 2026-07-18 擷取。

**ahern 個人實測(2026-05-22 → 2026-07-18)**——ahern 之 commit 集中於此段,最貼近 Weyver solo 情境|

| 面向 | 數值 |
|---|---|
| Calendar 跨度 | 2026-05-22 → 2026-07-18 ≈ **1.9 個月** |
| 活躍日 | **53 日**(近乎每日,對照 16-18 hr/day 強度)|
| Commits | ~961 ≈ 18 / 活躍日 |
| 行數變動 | **+209,974 / −45,953**(淨 ~164K;刪除僅 22% → 多為淨新增,非反覆重寫)|
| **峰值速度** | **淨 ~86K LOC / 月、~3,100 淨行 / 活躍日** |

**Weyver 範圍換算**|

| 標的 | LOC 估 | 對照(ahern 淨產出 ~164K / 2 月為 1 單位)|
|---|---|---|
| 完整 MVP(480 人月)| ~1.1M LOC | ~6.5 個「ahern 2-月衝刺」|
| Phase 1 完整 Ragic(~236 人月,land 既有客戶)| ~530K LOC | ~3.2 個「ahern 2-月衝刺」|

交叉驗證|1.1M LOC ÷ 480 人月 ≈ **2,290 LOC / 人月**,落在企業級手寫碼標準區間 → docs 之人月估與 LOC 估互相吻合。

**外推限制(為何不能天真放大峰值)**|

1. LOC 為粗糙代理,AI 生成碼較膨脹|直接 LOC→人月(86K ÷ 2,330 ≈ 37 人月 / 月)顯非真實,反證 AI-LOC 不等值於傳統人月。
2. ahern 該段部分產出為 demo / mockup 快碼(生成速度高於核心邏輯);Weyver 為財務正確性 / 合規 / 測試負擔重之 ERP,每行工時更高。
3. 53 / 57 天之強度不可能維持數年(對照 § 6 風險 3)。
4. Vernova 未達企業級硬化;Weyver **R1(Phase 1 完整 Ragic)** 之對外門檻(多租戶隔離 / 動態 DDL 注入防護 / 表單引擎正確性)更高,ERP 級(過帳不可變 / 對帳)門檻更在 Phase 2。

**校準結論**|

- § 1.3 之 ~36 人月-equiv / 年 就「純 Weyver focus」而言**偏保守**;實測峰值遠高於此。純 coding 產能不是瓶頸。
- **真正 binding constraint 非 coding 速度,而是導入 pipeline 之 attention-split**(§ 2、§ 3)。**校正**|依 § 3 時間軸,90-95% 導入密集期為 **2026-07 → 2026-12(~6 個月)**,2027-01 收斂、2027-02 進入穩定 R&D —— 非舊敘述之「前 ~1 年」(偏悲觀,已修正)。Vernova 證明專注時可快速產出可測 SaaS;Weyver 時程風險在**注意力分割,非打字速度**。

**(a) 純 Weyver focus 時程(未計 calendar 稀釋,理論上限)**|

| 情境 | 純 Weyver 有效產能 | 完整 MVP | R1 完整 Ragic |
|---|---|---|---|
| 加速(Vernova 峰值 ×0.5,ERP 難度折後)| ~43K LOC / focus-月 | ~2 年 | ~10 個月 |
| 務實(峰值 ×0.3)| ~28K LOC / focus-月 | ~3 年 | ~15 個月 |
| 保守(8 人團隊基準,對照)| 6.5 人月 / 月 | 5.5 年 | ~2 年 |

**(b) 校正後 calendar 稀釋模型(取代舊「前 ~1 年」,對齊 § 3 時間軸)**|

| 期間 | 月數 | Weyver focus 佔比 | 累積 focus-月 |
|---|---|---|---|
| 2026-07 → 2026-12 導入密集 | 6 | ~8% | ~0.5 |
| 2027-01 → 2027-02 收尾轉換 | 2 | ~35% | ~0.7 |
| 2027-03 起 穩定 R&D | — | 70%(維運常態)/ 90%(積極卸載 17 家維運) | 每 calendar 月 0.7 / 0.9 focus-月 |

**(c) 疊加稀釋後之 calendar 時程(自 2026-07 起算)**|

| 情境 | steady-state focus | 完整 MVP | R1 完整 Ragic |
|---|---|---|---|
| 加速 + 積極卸載維運 | 90% | **~2.7 年(2029 上半)** | **~1.5 年** |
| 務實 + 部分卸載維運 | 80% | ~4 – 4.5 年 | ~2 年 |
| 保守(8 人團隊,對照)| — | 5.5 年 | ~2 年 |

> **兩個槓桿,量級不同**——回答「實測產能高,為何 calendar 仍長」|
> 1. **校正前段稀釋**(舊「~1 年」→ ~6 個月密集期)|僅省 ~6 個月 calendar,**量級小**。
> 2. **穩定期維運拖累**(17 家 live 客戶常態吃 ~30% 專注)|**主導因子**。solo 若永久被維運吃 ~30%,完整 MVP calendar 難低於 ~4 年(務實);唯有將維運**卸載 / 自動化**至 ~90% focus,加速情境方可壓至 **< 3 年**。此即 § 6 風險 3 之延伸:solo 時程 bound 於**注意力配置**,非 coding 產能。
> **修正**|舊敘述「solo 務實 ~3–4 年 已快於 8 人團隊 5.5 年」係**未計稀釋之純 focus 值**;疊加維運稀釋後,solo 務實(~4–4.5 年)與 8 人保守(5.5 年)差距收斂。M18 之交付仍以 § 4 subset 為驗收標準,不因產能校準而改。

## 6. 三大風險

### 風險 1|導入業務吃時間超預期

**觸發**|既有 17 家中 1-2 家導入卡關(客戶端變更、bug、對接難題),開發者被拉入救火 → Weyver 時間歸零。
**對策**|本規劃已於穩定期占比預留 buffer,追加建議:

- 事前與客戶簽 change order,超出範圍不執行
- 挑 3 家最高風險客戶(最大金額 or 最新 ERP 對接)提前準備

### 風險 2|動態 schema 引擎(命門)複雜度超預期

**觸發**|Ragic 範式命門為 **runtime 動態建 / 改真實表(Tier-2)+ identifier 白名單注入防護 + 多租戶 RLS**(docs/15 / docs/16 / docs/21)。此為 Phase 1 最上游 blocking 投資,若卡關則整個 Ragic 平台 land 不了(docs/13 Risk Gate P0-1 = 最大 risk gate)。
**對策**|

- **月段 A 執行 1-2 週 spike**(驗證 runtime create/alter table + 參數綁定 + metadata catalog 白名單 + RLS FORCE 隔離)
- 若 spike 卡關,fallback 檢視 Baserow core / Teable packages(MIT)可 fork 之真實表引擎(docs/16),省數月;最劣採固定 schema 子集先 land 部分表單
- 動態 DDL 安全鏈為資安命門,提交架構 / 資安 review(見風險 4)

### 風險 3|16-18 hr/day 全職強度之健康與續航

**觸發**|**本規劃最大結構性風險**。16-18 hr/day × 週 6 日、持續 18 個月以上為極高強度工作模式,產業研究顯示 60+ hr/week 持續 3 個月以上普遍出現以下風險:

- 認知能力下降(判斷力、debug 效率、程式碼品質退化)
- 慢性壓力 → 睡眠障礙 / 免疫下降 / 心血管風險
- 職業倦怠(burnout),恢復期常需 3-6 個月
- 決策疲勞(decision fatigue)導致架構選擇偏差
- 家庭 / 社交關係承壓

**對策**|

- **強度分級預案**|區分「持續強度」與「衝刺強度」。16-18 hr/day 定為「衝刺級」,每次不宜超過 4-6 週,之間需安插 12-14 hr/day 恢復期
- **敏感性數字**|若強度中途降至標準 FTE 8 hr/day 持續 3-6 個月,18 月產出從 25 人月降至 18-20 人月(表單引擎核心 + 關聯 仍可完成,進階視圖 / pilot 遷移需順延 2-4 個月)
- **量化 checkpoint**|每 3 個月自我評估認知指標(專注時長 / debug 錯誤率 / 睡眠品質),連續 2 個 checkpoint 惡化即強制降強度
- 每季度 review 進度,允許 pivot / kill 決策
- 每半年安排 1 週 unplug
- 家庭 / 醫療支援系統事先建立

### 風險 4|Solo 認知盲點

**觸發**|單人執行全棧,無 code review / 無架構共議,錯誤架構決策無外部校正機制 → 後期發現需大幅重寫。
**對策**|

- 關鍵架構決策(dynamic schema / auth model / 多租戶隔離)提交資深架構 / 資安顧問 review
- Claude Code 用於程式碼 review(不同 session 執行「adversarial review」提出反面意見)
- 每 milestone(M6 / M12 / M18)寫短篇 architecture decision record,強制自我檢驗
