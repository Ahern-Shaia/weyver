## 1. 技術選型原則

### 1.1 頂層原則

1. **Solo dev + Claude Code 友善**|優先 TypeScript / Python(Claude Code 產能高),避免 Rust / Go 大量新學習
2. **開源優先**|**v5 全 OSS-only stack**(2026-07-16 決策)|不採任何商業授權軟體;所有 Enterprise features 由 self-host OSS or 自建補齊
3. **降低運維負擔**|managed services 優先(Cloudflare / Vercel / Supabase)少自建 infra
4. **穩定 > 新潮**|生產就緒優先於 bleeding edge;採 LTS / stable 版本
5. **模組化 / 可換掉**|每一層可獨立替換(如 ORM、Auth、Search)
6. **統一 language stack**|Frontend + Backend + Edge + **Weyver 自建 ERP CORE** 均 TypeScript(v2.0 revert v1.9,recover ERP CORE 但保 TS 純度,不 fork Odoo)
7. **企業級可接受**|Multi-tenant / 稽核 / SSO / TLS / GDPR 適用

### 1.2 拒絕的原則

- **拒絕 Serverless-first 主架構**|多租戶 SaaS + 長連線 WebSocket(現場即時) + Edge Gateway 對接不 fit Serverless。可用 Serverless 作 batch / cron
- **拒絕「Ragic / ERP / MES / ISO 四大微服務」**|見 § 1.3 架構決策(採 modular monolith)
- **拒絕自建 Auth / DB / Search 造輪子**|用成熟開源

### 1.3 架構決策|Modular Monolith(非微服務)⭐

**決策(2026-07-17)**|核心 app 採 **模組化單體(modular monolith)**,**不**把 Ragic / ERP / MES / ISO 拆成四個業務微服務。臃腫難維護靠**模組邊界**解決,不是靠**網路邊界**。

**為什麼不拆四大微服務**|

1. **Solo dev 拿全部成本、零團隊收益**|微服務本質是**組織擴展**解法(Conway's law),讓多團隊獨立部署。一人開發拆了只換來 N 套部署 / N 套監控 / 跨服務除錯 / 分散式交易 / 網路延遲 —— **維護變難**。
2. **打架「Ragic 為 substrate」架構**|ERP/MES/ISO 共用**同一表單引擎、同一動態 schema、同一公式與權限、同一 DB**(見 § 2 架構主張)。拆四服務 = 每服務一份引擎 + 互相遠端呼叫,把統一基底硬切開。
3. **賣點(整合)變分散式交易地獄**|「採購拋轉財會 / NCR 凍結庫存 / 生產工時結算成本」在單體是**單一 DB transaction**(原子、簡單);微服務則變 saga / 最終一致 / 補償交易。**最該緊耦合的東西不該拆**。
4. **韌性的真相**|單體跑**多實例 + 負載平衡 + health check** 一樣有容錯;真正單點故障是共享 Postgres / Redis —— 微服務**一樣全掛**,拆服務救不了。唯一真需「離線也能動」的是 MES Edge Gateway,**它本來就獨立**(廠內 store-and-forward)。

**該獨立的:按「技術特性 / scaling profile」而非「業務模組」**|

| 獨立單元 | 為什麼獨立 |
|---|---|
| **MES Edge Gateway** | 已獨立(客戶廠內 Docker,離線緩衝 store-and-forward) |
| **即時串流採集**(SCADA / MQTT ingestion) | 高吞吐串流,scaling profile 完全不同,不拖累 ERP UI |
| **背景工作 worker**(BullMQ:報表 / 對帳 / 電子發票上傳 / 通知) | 非同步、可獨立重啟、獨立擴 |
| **搜尋**(Meilisearch) | 本來就獨立 process |

核心 app(表單引擎 substrate + ERP 計算層 + ISO + MES 雲端管理)= **一個模組化單體,共用一個 DB**。

**路徑|Modular Monolith First**|NestJS 模組邊界(`ledger / inventory / production / quality / iso …`)畫清楚 → 解決臃腫難維護 + 跨模組零成本整合;未來若有**真實痛點**,再用 NestJS 內建 microservice transport 把某模組抽成獨立服務(邊界早已在)。業界共識:Shopify / GitHub / Amazon Prime Video 皆從微服務**退回**單體省成本。

#### 何時才該把某模組拆成微服務?(判斷表)

**下列條件**同時多項成立**才**拆;否則留在單體。

| 觸發訊號 | 說明 | 未達標則 |
|---|---|---|
| **獨立擴展需求** | 某模組流量 / 資源用量與其他模組差一個數量級(如即時採集 vs 表單 CRUD)| 留單體,水平擴整個 app |
| **獨立可用性需求** | 該模組故障必須**不得**波及其他,且無法靠多實例達成 | 留單體 + 多實例 |
| **獨立部署節奏** | 該模組改動極頻繁,每次連動全 app 重部署成本過高 | 留單體(CI 快即可)|
| **獨立技術棧** | 該模組需要不同 runtime / 語言(如 ML 推論、串流引擎)| 留單體 |
| **團隊邊界** | 有獨立團隊要 own 該模組、獨立 release | solo / 小團隊 → 留單體 |
| **資料邊界乾淨** | 該模組與其他跨模組交易極少,可容忍最終一致 | 跨交易多 → 留單體(否則 saga 地獄)|

> **判準**|少於 3 項成立 → 不拆。目前僅 MES 即時採集 + 背景 worker + Edge Gateway 達標(且多為 process 分離而非完整微服務),核心 ERP / 表單 / ISO **一項都不該拆**。

### 2.2 部署模式

**部署單元(modular monolith + 少數抽出 process,見 § 1.3)**|

| 部署單元 | 內容 | 部署 |
|---|---|---|
| **Weyver Core(模組化單體)** | 表單引擎 substrate + ERP 計算層 + ISO + MES 雲端管理 + Frontend BFF;NestJS 模組邊界清楚 | Cloud 多租戶,**多實例 + 負載平衡**(初期 Coolify on VPS;成長期 K8s) |
| **即時串流採集 service** | SCADA / MQTT ingestion(高吞吐,獨立 scaling)| 獨立 process / 容器 |
| **背景 worker** | BullMQ:報表 / 對帳 / 電子發票上傳 / 通知 | 獨立 process,可獨立重啟 / 擴 |
| **搜尋** | Meilisearch | 獨立 process |
| **MES Edge Gateway**(per-customer) | Node-RED + OPC-UA / MQTT / Modbus,對接廠內 SCADA / 機台;離線 store-and-forward | Docker 部署至**客戶廠內**;Weyver 管 image,客戶配憑證 |

- **共用**|Weyver Core + 抽出 process 共用**單一 PostgreSQL**(跨模組交易 = 單一 DB transaction,整合零成本);Redis(cache / queue / pub-sub)。
- **架構主張(2026-07-17)**|表單引擎為 substrate,ERP/MES/ISO 皆建構其上(單據 / 主檔 / 品檢 / 文件 = 表單 app;深層計算 = 計算層 NestJS services)。
- **拆分紀律**|Weyver Core 內的 ERP / 表單 / ISO **一項都不拆微服務**(見 § 1.3 判斷表);未來痛點驅動再抽。
- **Q 模組收斂**|客戶放棄原 ERP,不做常駐多 ERP 對接;至多 onboarding 一次性資料匯入。
- **Prod 雲端部署架構(AWS / GCP)+ 全服務成本**|見 **§ 16.5-16.11**(主推 GCP `asia-east1` 台灣;cloud-portable 不綁專屬服務;Tier E ~NT$14-22K/月)。

### 3.2 Web Framework(v3 update|升級為 NestJS + Fastify adapter)

**v3 決策**|由 v2 之「Fastify + tRPC」升級為「**NestJS 10.x + Fastify adapter + tRPC**」,呼應 user「企業級應用框架,安全、可靠」需求(見 docs/12 § 3.4)。

| 項目 | 選型 | 理由 |
|---|---|---|
| **App Framework** | **NestJS 10.x** | **企業級應用框架產業標配**|Angular-style DI + Modules + Guards + Interceptors + Pipes + Filters + Middleware;數千 enterprise SaaS production;結構化利於團隊擴編 |
| **HTTP Platform** | **Fastify adapter**(`@nestjs/platform-fastify`)| **90% Fastify throughput + 100% NestJS DX**;Fastify 為 3-4x Express,JSON Schema serialization + validation |
| Internal API | **tRPC** 11(與 NestJS controller 混用) | Type-safe RPC 為前後端零 schema 同步(選配|純內部 API 用)|
| External REST | NestJS controllers + `@nestjs/swagger` | 自動 OpenAPI 文件;Ragic-like 每張表單自動生成 REST |
| WebSocket | `@nestjs/websockets` + `@nestjs/platform-fastify` + Redis Pub/Sub | 即時通知、MES 現場資料串流 |
| Validation | **class-validator + class-transformer**(NestJS 原生)+ **Zod**(選配)| DTO 層強型別驗證 + runtime guard |
| DI Container | **NestJS 內建** | Testability 極佳(mock/inject),utility class 分離乾淨 |
| **RBAC / Auth Guards** | **NestJS Guards + Passport strategies** | 企業級權限控制內建 |
| **Interceptors**(logging/timeout/cache) | **NestJS Interceptors** | Cross-cutting concerns 標準化 |
| Rate Limiting | `@nestjs/throttler` | 官方支援 |
| Task Scheduling | `@nestjs/schedule`(cron / interval / timeout) | 官方支援 |
| Config | `@nestjs/config` + env / dotenv | 官方支援 |

**為什麼由 Fastify → NestJS + Fastify adapter**|

1. **企業級應用框架 defensible**|NestJS 是 2026 Node.js 企業級應用框架**產業共識標配**|對 pilot 客戶技術評審不需額外解釋
2. **安全內建**|Guards + Pipes + class-validator + RBAC + Interceptors 系統性 handle 安全 concerns
3. **可靠 = production proven**|LinkedIn、Adidas、Roche、Autodesk、Capgemini、Decathlon 等企業 production 使用
4. **Solo dev 之取捨**|+15-25% 上手 overhead,換來長期維護 / 擴編 / testability 大幅改善(對比 Fastify 之 minimal,solo 需自維護紀律)
5. **保留 Fastify 效能**|`@nestjs/platform-fastify` 讓 NestJS run on Fastify → 90% Fastify throughput + 100% NestJS DX(見 docs/12 § 2.3)
6. **Claude Code 產能|中等**|NestJS 語法穩定,Claude Code 熟(略遜於 Fastify 之熟悉度,但 acceptable)

## 4. ERP CORE 自建 + Q 客戶 ERP 升級 bridge(v4|Weyver 自建 一體 offering)

### 4.1 v4 決策|Weyver 自建全套 ERP CORE(不 fork Odoo,不看 Odoo source)

**docs/04 v2.0 拍板**|Weyver 為 Ragic + ERP + MES + ISO 一體 offering,缺一不可。Weyver **自建全套 ERP CORE**(J 財會 + K 進銷存 + L 生產 + M 品保 + N 成本 + O 電子發票 + P 進出口)。

**技術棧策略**|
- **仍拋棄 Odoo Python fork**(A2 決策不變)
- **統一 TypeScript 全棧**(含 ERP CORE)
- **Weyver ERP CORE 於 Weyver Core monolith 內**(NestJS Module 分區)
- **Domain knowledge 純合法學習來源**(見 §4.5)

### 4.2 ERP CORE 之 NestJS Module 分區

```
apps/api/src/modules/erp/
├── ledger/              # J 財會 (GL / AP / AR / 固資 / 匯兌 / 合併)
│   ├── entities/        # LedgerEntry, JournalHeader, AccountCode, ...
│   ├── services/        # LedgerPostingService, PeriodClosingService, ...
│   ├── controllers/     # REST + Swagger
│   ├── dto/             # class-validator DTO
│   └── ledger.module.ts
├── inventory/           # K 進銷存
│   ├── entities/        # StockItem, StockMovement, Location, ...
│   ├── services/        # ValuationService (FIFO/加權平均), ...
│   └── inventory.module.ts
├── production/          # L 生產 (BOM / WorkOrder / MRP)
│   ├── entities/        # BomHeader, BomLine, WorkOrder, ...
│   ├── services/        # BomExplosionService, MrpService, ...
│   └── production.module.ts
├── quality/             # M 品保 (批號 / 序號 / 追蹤)
├── costing/             # N 成本 (標準 / 分批)
├── einvoice/            # O 台灣電子發票合規
├── trade/               # P 進出口
├── bridge/              # Q 客戶 ERP 升級 bridge (原 Q Adapter Hub)
│   ├── adapters/        # tiptop.adapter.ts, chi-hang.adapter.ts, sap-b1.adapter.ts, ...
│   └── bridge.module.ts

```

**設計原則**|
- 每 sub-module 自 encapsulated,只透過 exposed Service / DTO 對外互通
- Domain entity 命名為 Weyver 原創(如 `LedgerEntry`,**不** 用 Odoo 之 `account.move.line`)
- 每 module 獨立 unit test + integration test

### 4.3 Q 模組|客戶 ERP 升級 bridge(v4 用途重新定位)

**v4 用途**|對 pipeline 17 家已有既有 ERP 之客戶,提供 **migration bridge**|

### 4.4 Q Migration bridge 最小契約

## 8. 動效系統(順暢舒適為主)

### 8.1 動效原則

1. **每個動效解一個問題**|不為動而動
2. **快 vs 慢有標準**|micro 150-250ms、macro 300-500ms、long 600-800ms(最多)
3. **一致的 easing**|進場 `ease-out`、退場 `ease-in`、雙向 `ease-in-out`
4. **支援 reduced motion**|`@media (prefers-reduced-motion: reduce)` 一律 fallback 至 fade-only
5. **避免**|full-page flip、heavy particle、3D transform、mouse follower、autoplay video

### 8.2 Duration & Easing 標準

```css
--duration-instant: 100ms;   /* 微觀 state change: hover / focus */
--duration-fast: 150ms;      /* button state / tooltip */
--duration-normal: 250ms;    /* dropdown / accordion / tab */
--duration-slow: 400ms;      /* modal / drawer / page section */
--duration-slower: 600ms;    /* page transition */

--ease-in-out: cubic-bezier(0.4, 0, 0.2, 1);  /* 標準 */
--ease-out: cubic-bezier(0, 0, 0.2, 1);        /* 進場 */
--ease-in: cubic-bezier(0.4, 0, 1, 1);          /* 退場 */
--ease-spring: cubic-bezier(0.34, 1.56, 0.64, 1); /* 微彈(success 用)*/
```

### 8.3 動效 library

| 用途 | 選型 |
|---|---|
| Complex animation | **Motion**(前 Framer Motion)12+ | 宣告式、layout animation 頂尖 |
| CSS animation | Tailwind + custom keyframes | 簡單場景 |
| List reorder | dnd-kit + Motion `AnimatePresence` | 拖拉排序 |
| Number count | **react-countup** | 儀表板 KPI |

### 8.4 Component 動效 patterns

**Modal / Dialog**|
```
enter: opacity 0 → 1(fade,duration-normal 250ms,ease-out)
       + scale 0.96 → 1(同期)
exit:  opacity 1 → 0(duration-fast 150ms,ease-in)
       + scale 1 → 0.96(同期)
```

**Drawer / Sheet(側滑)**|
```
enter: translateX(100%) → 0(duration-slow 400ms,ease-out)
exit:  translateX(0) → 100%(duration-normal 250ms,ease-in)
```

**Dropdown / Popover**|
```
enter: opacity 0 + translateY(-4px) → 1 + 0(duration-fast 150ms,ease-out)
exit:  opacity 1 → 0(duration-instant 100ms,ease-in)
```

**Toast(Sonner)**|
```
enter: opacity 0 + translateY(-16px) → 1 + 0(duration-normal 250ms,ease-spring)
自動消失: 4-6 秒後 fade out(duration-fast 150ms)
```

**Skeleton loading**|
```css
@keyframes shimmer {
  0% { background-position: -1000px 0; }
  100% { background-position: 1000px 0; }
}
duration: 1500ms linear infinite
```

**Button state**|
```
hover: bg subtle darken + opacity 0.9(duration-instant 100ms)
active: scale 0.98(duration-instant 100ms)
focus: ring 2px outline(duration-fast 150ms)
loading: spinner replaces text(duration-fast fade)
```

**Card entry(list)**|
```
初次渲染: stagger 30ms delay
individual: opacity 0 + translateY(8px) → 1 + 0(duration-normal 250ms,ease-out)
```

**Sidebar 展開 / 收合**|
```
width: 240px ↔ 64px(duration-normal 250ms,ease-in-out)
內容 opacity 同步(避免文字擠壓)
```

**Row 展開(展開子表)**|
```
height: 0 → auto(duration-slow 400ms,ease-out)
opacity: 0 → 1(同期,delay 50ms)
```

**Progress bar**|
```
width: N% smooth transition(duration-slow 400ms,ease-out)
```

**Number counter(KPI)**|
```
0 → target 500ms 內漸增(react-countup)
```

**Page transition(Next.js)**|
```
Route change: fade 100ms(超快,避免感覺卡)
不用 slide,SPA-like 感覺
```

**Focus ring**|
```css
:focus-visible {
  outline: 2px solid var(--color-accent);
  outline-offset: 2px;
  transition: outline-offset 100ms ease-out;
}
```

**Success confirmation**|
```
checkmark icon: scale 0 → 1(spring)
+ subtle green background pulse(one-shot)
```

**Grid cell edit(Glide Data Grid)**|
```
cell focus: 2px ring(duration-fast)
edit mode entry: no animation(立即,不干擾輸入)
save: subtle green flash 300ms
error: subtle red flash 300ms + shake(3px,150ms×2)
```

### 8.5 Reduced motion(A11y 必需)

```css
@media (prefers-reduced-motion: reduce) {
  *, ::before, ::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
  /* Modal / Dialog 仍需 fade,不用 scale;抖動類全去 */
}
```

### 8.6 反 pattern(禁用)

- ❌ Full-page 3D flip
- ❌ Particle 背景動畫
- ❌ Mouse follower
- ❌ Autoplay video / carousel
- ❌ Heavy parallax
- ❌ 過長動效(> 1 秒)於 UI 互動
- ❌ 同時 > 3 個元素動畫(視覺負擔)
- ❌ 每次頁面 load 都放 hero animation

### 8.7 動效效能

- 只 animate `transform` 和 `opacity`(GPU-friendly)
- 避免 animate `width` / `height` / `top` / `left`(觸發 layout)
- 大量 list 用 `will-change: transform`(慎用,memory 成本)
- Framer Motion 用 `layout` prop 智慧 detect
- 60fps 為底線

### 12.2 前端「模擬用戶操作」的解法 ⭐

**痛點**|前端最難的是反覆模擬使用者操作以驗證行為。解法分「開發當下」與「CI 回歸」兩軌:

**(a) 開發當下|AI 驅動真實瀏覽器(Playwright MCP)**
- Claude Code 連 **Playwright MCP**(`@playwright/mcp`)→ 直接驅動 Chromium:導航 / 點擊 / 輸入 / 讀 **accessibility snapshot** / 截圖 / 斷言。
- 迴圈|啟 dev server → AI 以使用者身分走流程 → 觀察結果 → 改 code → 再走 → 走通後**存成 Playwright spec**。讀 a11y tree(非純像素)故**穩定、可解釋、非 flaky**。
- 對齊 AGENTS.md「前端改動須啟 dev server、在瀏覽器實際用過才算完成」;搭配 `verify` / `run` skill。

**(b) CI 回歸|codified Playwright specs**
- AI 驅動瀏覽器**慢且非確定性 → 不放 CI**;CI 只跑 (a) 產出之確定性 Playwright spec + 元件測試。
- **分工原則**|AI 用來**探索 + 產生**測試;確定性測試把關 regression。

### 12.3 ⭐ Metadata-driven 生成式測試(Weyver 命門級槓桿)

**問題**|表單引擎 UI 由 `form_def / field_def` metadata **動態生成** → 客戶自建無限表單組合,**不可能為每張表手寫 E2E**。

**解法**|UI 既是 metadata 驅動,**測試也從同一份 metadata 生成**|
- 讀表單定義 → 自動展開互動情境:必填留空 / 型別錯 / 範圍越界 / **公式相依鏈** / **關聯 Link&Load 帶值** / 權限(欄·列可見性)/ 單據流狀態轉移。
- 手法|**property-based / 生成式測試**(**fast-check**,MIT)驅動 Playwright 或元件層;**metadata 一改,測試覆蓋自動跟上**。
- 綜效|動態 identifier 安全鏈(白名單 / `quote_ident`,docs/22 鐵則 1)可用**生成的惡意欄名 fuzzing** 驗證注入防線。

### 12.4 可重現性(讓上述全可重跑)

- **確定性 seed / factory**|每情境建立已知租戶 + 資料狀態(呼應 [[pitfall_serialized_column_breaks_whole_list]]:field-by-field 對 schema seed)。
- **MSW**(Mock Service Worker,MIT)|前端隔離測試時 mock API;整合測試才打真 DB(Testcontainers)。
- **凍結時鐘 + 固定亂數種子**|過帳 / 期結 / 報表 / idempotency 測試需確定性時間。

## 15. 技術棧選型 rationale

### 15.1 為什麼 TypeScript 為主(v2 update|拋 Odoo 後全 TS 統一)

- **Frontend 必須 TypeScript**(React 生態)
- Backend + Edge Gateway + Q Adapter 全部 TypeScript,solo dev 只需一種語言 mental model
- Claude Code 對 TypeScript 產能非常高
- 型別安全 end-to-end(Backend Zod schema → Frontend tRPC → Form validation)
- **v2 拋 Odoo fork(對比 v1)**|理由|
  - 用戶 pushback|「企業級軟體很少用 Python,目標是安全 / 可靠 / 性能 / 好維護」
  - Python + TS 雙語言對 solo dev 是真實 mental overhead
  - Python typing 弱(mypy 非強制),對比 TS static type 略遜
  - Node.js V8 CPU-bound 通常快 Python 3-5x
  - Python 於 enterprise 主流(YouTube / Instagram / Dropbox / Odoo 1000+ 集團),但 TS 於 modern SaaS 更合適
  - **docs/04 v1.9 拆 ERP CORE 決策後,fork Odoo 之收益消失**(Odoo 之 GL/AP/AR/BOM/MRP 全部不需要,直接對接客戶自帶 ERP 更 pragmatic)

### 15.2 為什麼 NestJS + Fastify adapter 而非 Fastify only / Express / Encore.ts(v3 update)

- Express|太老,middleware 生態鬆散,效能差
- **Fastify only(v2 之推薦)**|Solo minimal 適合,但**無 opinionated structure、無 DI、無 Guards / Interceptors**|對客戶 pitch「企業級應用框架」defensible 度中等
- **Encore.ts**|Rust runtime + zero-deps 很吸引,但**新興生態 + vendor commercial backing**|user 選擇「可靠」優先,退回 mainstream 選項
- **NestJS + Fastify adapter(v3 決策)** ⭐|
  - 「企業級應用框架」**產業共識標配**
  - DI + Guards + Interceptors + Pipes + Filters + Middleware 系統性 handle enterprise concerns
  - Fastify adapter 保留 90% Fastify 效能
  - 生產案例|LinkedIn、Adidas、Roche、Autodesk、Capgemini、Decathlon
  - 對「安全 / 可靠」目標 fit 最好
  - Solo dev +15-25% 上手 overhead 可接受(pilot 期間長期維護收益更大)

### 15.3 為什麼 Drizzle 而非 Prisma / TypeORM

- Prisma|Rust 引擎多一層、schema.prisma DSL 需學、Serverless cold start
- TypeORM|Legacy patterns、decorator hell
- Drizzle|SQL-like DSL(貼近 pgsql)、零 runtime cost、輕、TypeScript first

### 15.4 為什麼 shadcn/ui 而非 MUI / Ant Design / Chakra

- MUI / Ant Design|Google/Alibaba 觀感過強、customize 難、bundle 大
- Chakra|運行時 styling 效能 penalty
- shadcn/ui|copy&customize、無 dependency lock、Tailwind 生態、Radix A11y 內建、solo dev 完全掌控

### 15.5 為什麼 Motion 而非純 CSS transition

- 純 CSS|layout animation / list reorder / spring 難處理
- Motion|宣告式、layout prop 自動 detect、accessibility 內建、TypeScript first

### 15.6 為什麼 Glide Data Grid 而非 AG Grid Enterprise(v5 OSS-only)

- **v5 決策**|Weyver 一律免費 OSS 軟體;AG Grid Enterprise 商業授權移除

### 16.5 Prod 雲端部署架構(AWS / GCP)—— 總則

> **2026-07-18 新增**|dev 環境全本地(docker-compose,見 § 11.1),無議題。本節評估 **prod 環境**之完整部署架構,涵蓋 **AWS 與 GCP** 兩套參考方案 + 全服務成本。

### OSS-only 於雲端的意義(先釐清 vs § 16 決策)

**infra ≠ software license**。§ 16 之「OSS-only」指**不採商業軟體授權**(AG Grid / Sentry / Datadog / Vercel Pro);而 AWS/GCP 為**基礎設施即服務**——付的是 managed 託管與運算,非軟體授權費。二者不衝突,原則:

- **用 managed-OSS 服務**|RDS / Cloud SQL 跑的是 **OSS PostgreSQL**;ElastiCache / Memorystore 跑 **Valkey(MIT)**;ECS/Cloud Run 跑 **OSS 容器**。付託管費 ≠ 買軟體授權。
- **App-layer OSS self-host**|Meilisearch / GlitchTip / Infisical / Grafana·Prometheus·Loki / EMQX 於 utility VM 或容器 self-host(無 managed 版或 managed 為付費 SaaS)。
- **⚠️ 避開 proprietary lock-in**|**不用** Aurora 專屬功能 / DynamoDB / Cloud Spanner / 專屬 queue / 專屬 AI。全走標準 Postgres + 容器 + OSS → **cloud-portable**,可在 AWS↔GCP↔VPS 間遷移(呼應 [[feedback_roi_include_ops_governance]] 之 no-lock-in)。

### 為何由 VPS 升 managed cloud(承 § 16.3 pilot VPS 基準)

| 理由 | 說明 |
|---|---|
| **solo binding constraint = attention** | docs/07 §1.4 結論|solo 瓶頸是注意力非產能。**managed Postgres / 容器買回 ops 時間**(HA / 備份 / patch / failover 免自維)——此為成本躍升之主要正當性 |
| **企業 B2B ERP 之信任門檻** | 客戶財務 / 生產資料要 **data residency / 自動備份 / DR / 稽核**;hyperscaler 有 credibility 與合規背書(SOC2 / ISO 27001 底層)|
| **彈性 scale** | 多租戶成長期需自動擴縮、read replica、跨 AZ HA —— VPS 手動維運不可持續 |

**代價明列**|infra 月費由 VPS **~NT$300-3K** 升至 managed early tier **~NT$15-22K/月**(見 § 16.10)。**兩層 tier 策略**|pilot 期可續用 **budget tier**(cloud VM + Coolify,承 § 16.3);收費穩定後升 **enterprise managed tier**(本節)。

### 16.9 AWS vs GCP 對照與建議

| 面向 | AWS | GCP |
|---|---|---|
| **台灣 region(data residency)** | 東京 / 香港 / 新加坡(台灣區已宣布,GA 待查)| **⭐ asia-east1 彰化(在地)** |
| **容器 serverless(solo ops)** | ECS Fargate / App Runner | **⭐ Cloud Run**(scale-to-zero,ops 最低)|
| **managed Postgres** | RDS(避 Aurora)| Cloud SQL(避 Spanner)|
| **Tier E list 月費** | ~$760-860 | **~$600-700**(略低)|
| **生態 / 企業採用度** | **⭐ 最廣**,客戶指定 AWS 機率高 | 次之 |
| **lock-in 風險** | 低(若守標準服務)| 低(若守標準服務)|

**建議**|

- **主推 GCP**|理由 3:(1) **asia-east1 在台灣**——食品 / 製造客戶之 **data residency 合規**與延遲優勢明確;(2) **Cloud Run** scale-to-zero + 零節點管理,對 solo dev ops 負擔最低、early 成本最省;(3) Tier E 略便宜。
- **AWS 為強備案**|若特定客戶 / 投資方指定 AWS,或需 AWS 獨有生態;架構等價可搬。
- **鐵律|cloud-portable**|全走標準 Postgres + 容器 + OSS,**不綁任一雲專屬服務**——切雲或退回 VPS 之遷移成本低(no-lock-in)。
