## 2. 工作區首頁

### 2.1 🔴 首屏最大的區塊是收件匣,不是表單

「**待我簽核 423**」佔掉首屏約一半,列出六筆之後接「另有 417 筆待簽」。

`docs/24` 的裁定逐字是「**主要畫面 = 『自己建自己填』的表單資料庫,非 KPI 儀表板**」。
待簽核收件匣**不是儀表板,但也不是表單資料庫** —— 它是第三種東西(to-do list)。
一個 423 筆待辦的清單擺在首屏,實質效果是把工作區變成簽核佇列。

⚠️ **這條要小心**:待簽核確實重要,問題不在「有」而在「它是首屏主體」。
盤點不預設結論,只記下它與 docs/24 的張力。

### 2.2 🔴 待簽項目沒有語意標題

列出的是「**表單 #550 #1**」「表單 #552 #1」——
使用者看不出那是哪一張採購單、多少錢、誰送的。

這是資料問題(dev 種子資料沒有標題欄)還是渲染問題,**未查證** ——
但即使是種子資料的鍋,「標題取不到時退回 `表單 #550`」本身就是一個需要處理的狀態。

### 2.3 品牌敘事句出現在產品畫面裡

> 「採購、財會、生產、品保 —— 散落的線頭,織成同一朵雲。 同一個工作區、同一套權限與稽核,切換像切分頁。」

這句話是 `docs/26` 的品牌故事,屬於**對外敘事**。`docs/26` 自己寫的邊界是
「織雲故事與隱喻邊界(存於敘事**非介面裝飾**)」。
而 memory `feedback_no_dev_phase_in_product_ui` 記過同型:產品 chrome 裡不放 sales-deck 內容。

### 2.4 144 張表單用扁平卡片牆瀏覽

分類「採購 63」底下直接鋪卡片,且出現「供應商 (2) (3) (4)」「請購單 (2) (3)」這類重複命名。
63 張卡片一屏放不下,而卡片上只有名稱 + 更新日期 —— **沒有任何可以據以區分的資訊**。

⚠️ 重複命名多半是 dev 資料造成的,但「同名表單如何區分」在 144 張的規模下是真問題。

### 2.5 「晚安」問候語

消費級 SaaS 的手法。`docs/26` 的聲音語氣定為 **sober**,兩者有張力。
—— 這一條**份量最輕**,列出來只為完整。

## 3. 表單設計器

### 3.1 🔴 同一屏有五組導覽

| # | 位置 | 內容 |
|---|---|---|
| 1 | 最左圖示欄 | 4 個**無文字標籤**的圖示 |
| 2 | 頂欄左 | 我的表單 / 範本 / 匯入 Excel / **+ 新增** |
| 3 | 頂欄右 | 設計 · 填單 · 網格 · 資料 |
| 4 | 第二欄 | 表單清單(搜尋 + 分類 + 144 項) |
| 5 | 第三欄 | 欄位型別面板(搜尋 + 常用 / 其他) |

**頂欄左右兩半是兩種完全不同性質的東西**:左半是「**建**一張新表的三條路」,
右半是「**看**當前這張表的四種模式」。它們擠在同一條 chrome 上,而且沒有任何分界。

### 3.2 🔴 最左圖示欄沒有文字標籤

4 個圖示、零標籤,在一個 144 張表單的工作區裡是主導覽。
⚠️ 這同時是 a11y 問題(`docs/frontend-design-principles` §A)與可學習性問題。

### 3.3 🔴 2D 畫布在欄位多時退化成一維長條

實測(45 欄位的表單):「項目1 … 項目22 …」**每列只放一個欄位、右側大片空白**。
2D 畫布的價值在「把單號與日期排在同一列」,但**新增欄位的預設落點是自己接一列**
(`form-geometry.ts` 的 `effectiveLayout` 逐字:「沒有版面資料的欄位一律往下接一列、佔半寬」)。

於是:**欄位一多,設計器看起來就跟一維清單沒有兩樣**,而使用者要手動把它們一個一個拖成兩欄。
—— 這是 IA / 互動問題,不是視覺問題,**換視覺方向不會改善它**。

### 3.4 儲存的位置不唯一

畫布右上有「儲存版面」,而頂欄也有一組操作。
「我改的東西存到哪、按哪個鈕」在同一屏有兩個答案。

## 4. 這份盤點的邊界(誠實記帳)

- **只走了五個畫面**。列表頁的檢視切換、看板 / 行事曆 / 樞紐 / 圖表、設定中心的其餘分頁**都沒走**。
- **dev 資料污染**:最近使用全是「PDF手測單 / 網格手測 / 群組欄手測」這類測試表單,
  重複命名也多半是我方測試造成的。凡是可能由資料造成的,上面都標了。
- **沒有使用者研究**。以上全部是對照自家文件(`docs/24` / `docs/26`)推出的張力,
  **不是**「使用者說難用」。要當成假說,不是結論。
- ⚠️ **未查證**:待簽核項目的標題為何是 `表單 #550`(資料 vs 渲染)。

## 5-bis. 2026-08-06 裁定與 A/B 實測

**裁定**|(a) `docs/37` 四方向錦標賽**作廢** —— 主畫面不是單據;
(b) 主視覺改採 `docs/mockups/workspace-ragic.html`,理由「脫離後台感、更有產品力」;
(c) 該稿的四項 `docs/14` 一票否決全採,但**先做 A/B 對照**再定尺度。

### 🔴 A/B 對照的實測結果:差距比預期小得多

`docs/mockups/workspace-ab.html` —— **同一份 DOM、同一份資料、同一個版面**,
只換四項:圓角 · 狀態章形狀 · resting 陰影 · 公式欄底色。
A = ragic 稿尺度;B = `tokens.css` v4 實際值(且照它自己的「殼靠面、單據靠框」,
所以 B 的側欄選取**一樣是色底**,不是稻草人)。

截圖:`docs/research/ia-audit-2026-08-06/ab-a.png` · `ab-b.png`。

**看下來兩版是同一個產品。** B **並沒有**讀成「公司內部後台」。

**推論**|讓 `workspace-ragic` 顯得「有產品力」的,是它的**結構**——
三欄各司其職 · 業務分組側欄 · 網格為主屏 · 右側明細帶子表與過帳 ——
**不是** 7px 圓角與 pill。

⚠️ 這一條值得記,因為 `tokens.css` v4 檔頭逐字寫著「起因:**review 三次指出畫面
『像公司內部後台、沒有品牌感』**」。同一個診斷至今四次,前三次的答案是
加顏色 → 色彩模型化 → 做工藝不加裝飾。**A/B 顯示第四次的答案(加裝飾)可能也不是主因。**

### C 版:測「層級」這個假設

`docs/mockups/workspace-abc.html` 第三段(截圖 `abc-c.png`)。
C = **B 的色彩 + 把字階與間距節奏拉開**,只從 A 取回一項(公式欄底色,理由是資訊非裝飾)。

實測三版的 computed style:

| | A | B | **C** |
|---|---|---|---|
| 標題 | 17px / 650 / −0.3px | 17px / 650 / −0.3px | **24px / 500 / −0.4px** |
| 內文 | 12.5px | 12.5px | **13px** |
| **標題 ÷ 內文** | 1.36× | 1.36× | **1.85×** |
| 列高 | 39px | 37px | **34px** |
| topbar | 48px | 48px | **56px** |
| 殼內距 | 16px | 16px | **24px** |

🔴 **注意最後三列的方向是相反的**:C 的**殼變鬆**(48→56 / 16→24)而**資料變緊**(39→34)。
這一點很重要,因為 `docs/14` line 20 的一票否決裡有「**大留白**」——
C **不是**加留白,是把兩套語言的密度分開。密度差本身就是層級,
而那正是 `tokens.css` v4「殼靠面、單據靠框」的延伸:兩套語言不該只有顏色不同。

**字重的依據**|`docs/37 §1` 實測結論①逐字「**重量感來自尺寸,無人用 900**」。
A/B 現況是 17px / wght **650** —— 小而重,正好與四站相反。C 改成大而輕(24px / 500)。

### 🔴 C 被推翻(2026-08-06 決策方看過:「完全錯誤,更像後台」)

**假設「後台感 = 沒有層級」錯了。** 記在這裡,因為這是一個有價值的否定結果。

**錯在哪,具體三條**:

1. **C 的版型正好是 admin panel 的招牌**|大而輕的頁面標題 → 留白 → 分頁列 →
   工具列 → 密表格,四層水平帶各用一條橫線隔開。Django admin / Rails admin /
   WordPress admin 全是這個形狀。把「層級」實作成「標題放大 + 留白拉開」,
   做出來的就是後台。
2. **我把表頭底色拿掉了**(`thead th{background:var(--card)}`),只留一條底線 ——
   那是**沒上樣式的 HTML table**。灰底表頭是「有人設計過」的訊號,被我親手拆掉。
3. **列高壓到 34px**|密度是 ERP 的訊號不是產品的訊號。Linear / Attio 的列反而更鬆。
   資料區因此更像 raw dump。

**修正後的假設(待驗)**|**後台感 = 網頁感**。
A 之所以像產品,可能是**圓角 + resting 陰影 + 緊湊的殼**讓它讀成一個
「應用程式視窗」,而不是「一個放了表格的網頁」。
旁證:工具型產品(Linear / Figma / Notion)的檢視標題**都是小的、內嵌在緊湊工具列裡**,
沒有一個用大頁面標題 —— 大頁面標題是網站與後台的模式,而我剛好做了那個。

⚠️ 這條修正**仍是假設**,而且是我第二次提假設。上一次錯了。

### D 版:照決策方圈的三條觀察做(不是照我的假設)

問「後台感最強的訊號是哪一個」,決策方圈了三條,而且**沒有圈**我修正後的假設
(「像網頁不像應用程式」)。所以 D 不照那條做,照這三條:

| 觀察 | D 的作法 |
|---|---|
| **① 色彩太素 / 太灰** | 色彩改為**承載資訊**:領域色(側欄分組,回答「這張表屬於哪塊業務」——144 張時這是導覽資訊)· 欄位型別色(`#` `$` `fx` `↗`,回答「這一欄是什麼」)· 狀態色。**每個顏色都要能回答一個問題,答不出來就不上色** |
| **② 元件粗糙 / 像預設控件** | **真 Lucide 圖示**(A/B/C 用的是 `▦` 這個 Unicode 字元)· **自繪 checkbox**(預設 `<input>` 是「沒被做過」最明顯的證據)· 輸入框有 hover / focus 態 · 按鈕有 inset 高光 |
| **③ 資訊堆太滿 / 沒重點** | 網格是唯一主角:主區底最亮(`--s1`)、側欄與明細退到 `--s2`。**靠底色與飽和度分主次,不是靠留白**(C 的教訓)。四層水平帶併成兩層 |

⚠️ **C 的教訓已避開**:不放大標題(改內嵌工具列,14.5px)、不加留白、列高回到 38px。

⚠️ 我已經猜錯兩次,這一版**不下結論**。截圖 `d-ver.png`。

### 唯一一項 A 有功能論據的

**公式欄整格上色**。A 的淡綠底讓「哪些數字是算出來的」一眼可見,
而 Weyver 的向上軸正是「算」(`docs/18`)。這一項不是裝飾,是**資訊**。
其餘三項(圓角 / pill / 陰影)目前只有 vibe 論據。

## 5. 與四個視覺方向的關係

`docs/37` 的 D1–D4 差異「**只在視覺世界觀**」(該文逐字)。對照本盤點:

| 本文列的問題 | 換視覺方向能不能解 |
|---|---|
| 2.1 首屏是收件匣 | ❌ 不能 —— 那是資訊架構決策 |
| 2.3 品牌文案在產品畫面 | ❌ 不能 —— 那是文案決策 |
| 2.4 144 張表單怎麼瀏覽 | ❌ 不能 |
| 3.1 五組導覽 | 🟡 **D2 例外** —— 它以報頭式頂欄取代側欄,是四案中唯一動到這一條的 |
| 3.2 圖示欄沒標籤 | 🟡 同上,D2 沒有側欄 |
| 3.3 2D 畫布退化成長條 | ❌ 不能 |
| 3.4 儲存位置不唯一 | ❌ 不能 |

**結論**|七條裡**五條與視覺方向無關**。
先圈選視覺方向再落地,解掉的是另一組問題;這七條需要各自的裁定。
