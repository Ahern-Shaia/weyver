# Weyver 兩層解耦出貨策略

> **文件性質**|出貨 / 排序策略。承接 docs/15 兩層資料模型 + docs/16 OSS 實證 + docs/18 計算層,提出**最大的難度降低 + 提早營收槓桿**:先出 ERP 價值,後補動態引擎。
> **配套**|docs/13(build order)+ docs/15(兩層)+ docs/16(OSS)+ docs/18(計算層)+ docs/07(時程)。
> **版本**|2026-07-18 v1

---

## 0. 核心洞見

**Tier-1(ERP/MES/ISO 系統實體)是固定 schema —— 它根本不需要 form-engine 的三塊硬骨頭就能跑。**

form-engine 最難、最有風險的三塊(docs/15/16)是:**動態 DDL、canvas Excel grid、公式引擎**。但這三塊是為了 **Tier-2(使用者自建表單)** 的**彈性**存在的。**Tier-1 的 ERP 實體 schema 固定、由 Weyver 預建**,用標準工具(Drizzle 固定表 + shadcn 表單 + TanStack 讀取表)就能做出來,**低風險、Claude Code 高倍率**。

→ **策略**|**先出「能賣的整合 ERP+MES+ISO」(Track A,不含三硬骨頭),把動態引擎(Track B,含三硬骨頭)放平行 / 後續軌道。** 客戶提早拿價值;最危險的命門不擋營收。

---

## 1. form-engine 能力拆解:關鍵路徑 vs 可延後

| 能力 | 首次出貨關鍵路徑? | 風險 | 說明 |
|---|---|---|---|
| **metadata 驅動渲染**(讀 metadata → 出 form/grid/view/API)| ✅ 關鍵 | 低 | 兩層都要;標準 React + metadata |
| **Tier-1 固定表**(ERP 實體)| ✅ 關鍵 | 低 | Drizzle 標準表 |
| **ERP 計算層**(docs/18)| ✅ 關鍵(ERP 價值)| 中 | domain 邏輯,非引擎難點 |
| **標準表單 / 讀取表 UX**(shadcn form + TanStack Table)| ✅ 關鍵 | 低 | 撐 Tier-1 的 CRUD |
| **ERP 實體 custom fields**(JSONB ext 欄)| ✅ 關鍵(早期彈性)| 低 | 給早期彈性,不需動態 DDL |
| **動態 DDL**(使用者 runtime 建 / 改表)| ⏸ 可延後 | **高** | Tier-1 不需要 |
| **canvas Excel grid**(格編輯)| ⏸ 可延後 | **高** | ERP 先用讀取表 + 表單 |
| **使用者表單設計器**(拖拉建表)| ⏸ 可延後 | 中高 | Tier-1 表由 Weyver 預建 |
| **完整公式引擎**(跨表 / 依賴圖)| ⏸ 多數可延後 | 中高 | ERP 計算走 docs/18 計算層 / 固定 SQL;使用者公式後補 |

**結論**|**三塊硬骨頭(動態 DDL / canvas grid / 使用者公式)全部可延後**,不擋首次出貨。首次出貨只需:metadata 渲染 + 固定表 + 計算層 + 標準 UX + custom fields。

## 2. 兩軌出貨計畫

### Track A|ERP 價值(先出、低風險、能賣)

- **內容**|整合 ERP + MES + ISO 在固定 Tier-1 表上跑;metadata 驅動渲染;標準表單 + 讀取表 UX(design system docs/14);計算層(GL/AP/AR/估值,docs/18);ERP 實體 custom fields(JSONB)給早期彈性;統一 shell(頂欄 + 導航,docs/14)。
- **客戶得到**|**一個整合的、可用的、可賣的 ERP+MES+ISO**,取代他們分散的系統 —— 定位的核心承諾**先兌現**。
- **風險**|低(標準工程,Claude Code 高倍率)。**不需通過 P0-1 動態 schema gate。**

### Track B|動態引擎(平行 / 後續、高風險、差異化)

- **內容**|三塊硬骨頭 —— 動態 DDL(Tier-2 使用者建表)+ canvas Excel grid(fork Teable MIT)+ 使用者表單設計器 + 完整公式引擎(fork Teable MIT ANTLR)。
- **客戶得到**|**Ragic 級自助彈性** —— 自建任意表單、Excel 式編輯、自訂公式。
- **落地**|Track B 完成後,(a) 使用者可建自己的表單;(b) **Tier-1 ERP 實體「rebase」到完整引擎**,連 ERP 也變可深度客製 —— 因設計系統延續(docs/14),視覺無縫。

```
時間 ──────────────────────────────────────────►
Track A  ██████████ 出貨(ERP+MES+ISO 可賣)──── 收費 ──►
Track B       ░░░░░░░░░░░░ 動態引擎(spike→建)──── 上線 Ragic 彈性 ──►
                                              ▲ rebase ERP 到引擎(視覺無縫)
```

## 3. 防重工架構(關鍵 —— 別讓 Track A 變拋棄式)

Track A 不能是「之後全砍掉重寫」。四個防重工設計:

1. **metadata 驅動從第一天**|即使 Tier-1 是固定表,UX 也走 metadata 渲染(form_def/field_def 描述固定表)。→ Track B 的引擎只是**擴充 metadata 能力**(加動態 DDL),渲染層不重寫。
2. **固定表 = 未來 Tier-1 表**|Track A 建的固定 ERP 表,就是引擎日後讀的同一批 Tier-1 表(docs/15)。schema 不變 → 零遷移。
3. **設計系統延續**(docs/14)|Track A / B 同一 token + component,視覺一致;lite UX(shadcn form / TanStack)與 full UX(canvas grid)是**同一設計語言的漸進能力**,非兩套。
4. **Component contract**|Track A 的 form / grid / detail 元件對「metadata + 資料 API」的介面,與 Track B 引擎產出的介面一致 → 換底層不換上層。
5. **custom fields 走 JSONB ext**|Track A 的早期客製用 JSONB overflow 欄(docs/15),Track B 動態 DDL 上線後可選擇性「實體化」熱門自訂欄 —— 平滑升級,非重做。

> **一句話**|**「先用固定表 + 標準 UX 出 ERP,但一切走 metadata 驅動 + 同一設計系統;動態引擎是後加的能力層,不是重寫。」**

## 4. 修訂 phasing(相對 docs/13)

docs/13 原序:form-engine 全做(P0-1..P0-5,75 人月)→ 再做 ERP(P0-6+)。**問題**|P0-1 動態 schema(最大 risk gate)擋在所有營收前面。

**解耦後的序**(不改總 scope,改順序 —— 前置價值、後置風險)|

| 階段 | Track A(關鍵路徑)| Track B(平行) |
|---|---|---|
| **Foundation** | metadata 渲染框架 + 固定表基建 + shell | (spike 三硬骨頭,docs/15 §12)|
| **Phase 0** | ERP 核心(GL/AP/AR + 進銷 + 工單)+ MES 現場 + ISO 文管 + 電子發票,**全固定表 + 標準 UX + custom fields** → **可上線收費** | 動態 DDL + canvas grid PoC(Teable MIT fork 驗證)|
| **Phase 1** | ERP 補完(FX/成本/MRP,計算層 docs/18)+ 各模組深化 | 完整動態引擎 + 使用者表單設計器 + 公式引擎 → **Ragic 彈性上線** + ERP rebase |
| **Phase 2** | 對標 features | AI 建表助手(docs/17,吃引擎的 metadata 生成)|

**戰略成果**|**P0-1 動態 schema gate 移出「首次營收」關鍵路徑** —— 即使引擎 spike 卡住,Track A 的 ERP 照樣能出、能收費,引擎慢慢磨。

## 5. 風險與緩解(誠實)

| 風險 | 說明 | 緩解 |
|---|---|---|
| **重工** | Track A 之後被引擎取代 | § 3 五道防重工設計;固定表零遷移,UX 是漸進能力層非重寫 |
| **定位稀釋** | 早期 ERP 不如 Ragic 彈性,削「Ragic 為基底」賣點 | 早期給 **custom fields 級彈性**;客戶期望排序(§ 6);pilot 首要需求是整合 ERP,非自建表 |
| **雙 UI 路徑** | lite UX + full engine 變兩套維護 | 讓 lite 是 full 的**子集**(同 metadata 渲染 + 同設計系統),一條路徑漸進,非兩套 |
| **公式缺口** | 早期無使用者公式 | ERP 計算走 docs/18 計算層 / 固定 SQL;使用者公式 Track B 補 |

---

## 6. 客戶期望排序(GTM 敘事)

對客戶 / pilot 的溝通順序,避免「怎麼還不能自建表單」的落差:

1. **先講整合**|「你分散的 ERP+MES+ISO,先在一個平台整合、能用、能取代舊系統」← Track A,pilot 首要需求。
2. **早期彈性**|「ERP 各表可加自訂欄位,依你流程調整」← custom fields。
3. **完整自助**|「接著開放:自建任意表單、Excel 式編輯、自訂公式 —— 完整 Ragic 彈性」← Track B,progressive rollout。
4. **AI 加速**|「再來:貼舊 ERP 畫面,AI 幫你搬」← docs/17。

> **pilot(鮮勇)首要痛是「多系統反覆切換」,不是「不能自建表單」** —— Track A 先解主要痛,Track B 補差異化,順序對。
