## 0. 這份文件要解掉的認知錯誤

**「全框線」是欄位表(單據)的視覺簽名,不是整個 app 的規則。**

docs/14 把「全框線欄位表」列為視覺簽名 —— 那句話講的是**單據**:
對應紙本表格、對應會計逐格核對,框線在那裡承載「這一格是一個獨立的欄位」的語意。

實作時這條被當成**全域**風格套用:導覽軌邊、面板欄邊、卡片邊、輸入框邊、
表格線全部用同一個 `--color-line`。結果整個畫面變成一張沒有層級的網格。

**兩套語言必須分開**:

| | 單據語言(欄位表 / 記錄頁 / 列印) | 殼語言(導覽 / 面板 / 工具列 / 清單) |
|---|---|---|
| 層級靠什麼 | **框線**(每格獨立,對應紙本) | **面**(底色階差)+ 空間 |
| 框線用量 | 高 —— 那是它的語意 | **極低** —— 只用在真正需要切分處 |
| 依據 | docs/14 視覺簽名 | 本文件 |

## 2. 🔴 量測結果(同一支腳本、同一個視窗尺寸 1600×1000)

| 指標 | Directus | Weyver 設計器 | Weyver 首頁 |
|---|---|---|---|
| 可見元素數 | 680 | 398 | 379 |
| **有邊框的元素** | **20(2.9%)** | **78(19.6%)** | 60(15.8%) |
| 字級種類 | **2**(13 / 14) | 5 | 5 |
| 主要內文字級 | 13px(佔 93%) | 12px(佔 58%) | 14px(佔 49%) |
| 常見底色階 | 白 / `#f0f4f9` / `#f7fafc` | 白 / `#f4f6f8` | 白為主 |

**三個結論**

1. **邊框密度差 7 倍。** 我方每 5 個可見元素就有 1 個被框起來;Directus 是每 34 個才有 1 個。
   這是「雜亂」的量化解釋 —— 不是元素太多,是**每個元素都在宣告自己的邊界**。

2. **字級種類越少越穩。** Directus 只用兩種字級就撐起整個介面,層級靠**顏色深淺與位置**。
   我方五種字級卻沒有層級感,因為層級被邊框的噪音蓋過去了。

3. 🔴 **「文字緊湊」不是字級太小。** Directus 的內文是 **13px,比我方的 14px 還小**,
   但不緊湊。**前一輪把 12→14 的方向是對的(12px 寫內文確實違反 §2.5),
   但誤以為那能解決緊湊感** —— 緊湊感來自邊框密度與缺乏留白分組,不是字號。

## 3. 殼的五條規則(可檢查)

| # | 規則 | 判準 | 為什麼 |
|---|---|---|---|
| **S1** | **殼的邊框佔比 ≤ 6%** | 可見元素中帶 border 者的比例,**只排除兩類**:(a) 單據語言的欄位表 / `table` (b) `input / select / textarea`(**文字輸入**)。**按鈕、清單項、面板項一律計入** | 見下方「判準是怎麼定錯又修正的」 |
| **S2** | **層級靠面不靠線** | 相鄰區塊以底色階差區分;僅在**跨越功能邊界**時用一條線 | 三階近乎無差的灰(白 / 極淡 / 淡)足以表達三層 |
| **S3** | **同時可見的輔助面板 ≤ 1** | 右側恆為 0 或 1 欄;多個設定改為**同一欄內的摺疊區段** | Directus 的 Layout Options / Auto Refresh / Import-Export 是**同一欄的三個 accordion**,不是三欄 |
| **S4** | **主體佔內容區 ≥ 60%** | 畫布 / 表格 / 記錄的寬度佔比 | 目前設計器畫布約佔 190/850 ≈ 22%,**主體是全畫面最窄的一欄** |
| **S5** | **水平 header 帶 ≤ 1 條** | 次要動作進 overflow menu 或就地浮層 | 目前設計器有 3 條(標題列 / 加入欄位帶 / 工具列),吃掉 ~130px 垂直空間 |

#### ⚠️ 判準是怎麼定錯又修正的(值得記,因為差點放行壞畫面)

初版判準是「所有帶 border 的可見元素」。試片首次量測 6.5% 超標,查組成發現 7 個裡有 4 個是輸入框 ——
**空輸入框的邊框是 WCAG 1.4.11 強制的**(docs/14 §2.4,`--color-line-input` 須達 3:1),
那不是「容器在宣告邊界」。於是把控件排除。

🔴 **但那一版順手把 `button` 也排除了,結果現行設計器由 19.6% 變成 3.3% —— 直接「合格」。**
而那正是 review 兩次指出有問題的畫面。回頭看組成:**78 個帶框元素中有 65 個是按鈕** ——
清單項、面板項、工具列鈕全都自己畫一個框。Directus 在同一指標下只有 1 個。

**按鈕不需要框線**(它有填色、標籤、hover 三種可供性);**空的文字輸入需要**(它可能什麼都沒有)。
判準因此定為:只排除文字輸入。

| 判準 | 試片 | 現行設計器 | Directus |
|---|---|---|---|
| 全部帶框 | 25.0%(含單據表) | 19.6% | 6.4% |
| ~~也排除按鈕~~ **(錯)** | 2.8% | **3.3% ← 假合格** | 4.3% |
| ✅ **只排文字輸入** | **2.8%** | **19.6%** | 6.4% |

**教訓**|訂量化門檻時要拿**已知有問題的樣本**去驗判準 —— 判準若讓壞樣本過關,錯的是判準不是樣本。

**留白的分組尺度**(對應「文字緊湊」)|組內 4px · 組間 12px · 區段間 24px。
目前全庫是 8–12px 一體適用,所以所有東西看起來一樣近 = 沒有分組 = 雜亂。

## 4. 品牌識別的重新定位

**「chrome 上主色」不等於品牌識別。** 深色側欄 + 白色多欄是 AdminLTE / cPanel /
Bootstrap admin 十五年來的原型 —— 它是**最沒有作者性**的一個手勢,
2026-08-01 的樣板因此**加強**了「內部後台」的印象而非減弱。

品牌識別的載體應該是**有作者性、且競品不會長一樣**的地方:

| 載體 | 說明 |
|---|---|
| 標誌與品牌鎖定用法 | 出現的位置、比例、與產品名的關係(非只是一個色塊) |
| **標題排版** | 字重 / 字距 / 與內文的比例 —— 這是「聲音」 |
| **空狀態** | 使用者最常看到、也最少人做好的畫面 |
| **列印抬頭** | Weyver 的單據會被印出來、被稽核 —— 那是品牌真正被外部看見的時刻 |
| 一個可辨識的結構手勢 | 例如全框線欄位表本身(**用在單據上**)就是我方的簽名 |

⚠️ **裁定待定**|導覽軌是否保留主色深底,應在 S1–S5 落地後**重新評估** ——
在一個邊框 2.9%、層級靠面的畫面裡,同一個深色側欄的觀感可能完全不同。
**不要在殼還沒修好之前爭論顏色。**

---

## 5. 落地順序(建議)

1. **S1 + S2**|把殼的邊框拆掉,改用底色階差。這是單一最大槓桿(19.6% → 目標 ≤6%)。
2. **S3**|三個輔助面板 + 欄位設定改為右側單欄 accordion。
3. **S5**|三條 header 帶收成一條。
4. **S4**|前三項完成後主體佔比自然回升,再量一次確認 ≥60%。
5. **留白分組**|4 / 12 / 24 三級尺度取代目前的一體適用。
6. 重新評估品牌載體(§4),此時再談導覽軌顏色。
7. ⏳ 補 Appsmith / ToolJet 實走 —— 建構器版面是設計器的直接對位,目前仍缺。

**每一項都要有量測前後對照**,不接受「看起來好多了」。
