## 1. 現況:Weyver 一共只有四個 surface

| Surface | 路由 | 裡面有什麼 |
|---|---|---|
| **工作區** | `/app` | 分類目錄首頁 · 最近使用 · ⌘K · 通知鈴鐺 · status bar |
| **設計器** | `/app/builder` | 欄位設計 / 2D 版面 / 欄位設定 / 條件式格式 / 型別轉換 · **動作按鈕** · **簽核定義** · **標籤設計** · **列印設定** · Excel 匯入建表 · 記錄面板(表單/網格/清單) |

| **設定中心** | `/app/settings/*` | 12 頁:公司 / 成員 / 權限 / 通知設定 / 通知通道 / **公開表單** / 整合(Webhook·API 金鑰)/ 資料匯出 / 回收桶 / 帳號安全 / 簽核代理人 / 個人設定 |

另有一條獨立列印路由:`/app/forms/[formId]/labels/[labelId]/print`。

## 2. 🔴 IA 錯位:三處,而且性質不同

### 2.1 per-form 的設定放在租戶設定頁,靠下拉選對象(**最該修**)

對碼查證(`apps/web/src/app/app/settings/`):

| 設定 | 實際粒度 | 現在住哪 | 問題 |
|---|---|---|---|
| **公開表單** | **per-form**(`formId` 為必要參數) | `/app/settings/public-forms` | 使用者人在表單上,想把**這張表**公開,卻要離開表單 → 進設定 → **再把同一張表單選一次** |
| **通知設定** | 有 per-form 層(`scope === "form"` + 表單下拉) | `/app/settings/notifications` | 同上。租戶層那一半放這裡是對的,**表單層那一半不是** |
| Webhook / API 金鑰 | 真·租戶級(端點 + 事件型別,不綁表單) | `/app/settings/integrations` | ✅ **放對了**,不要動 |

**這不是缺功能,是入口反了。** 兩者都已 SHIPPED、都能用,只是使用者找不到 ——
而「找不到」與「沒有」對客戶而言沒有差別。

### 2.2 表單層動作散在設計器與檢視兩邊

| 動作 | 現在住哪 | 心智上該在哪 |
|---|---|---|
| 匯出 Excel · 批次刪除 | 表單檢視工具列 | ✅ 對 |
| 匯入既有表單 | 表單檢視 | ✅ 對 |
| **標籤設計 · 列印設定** | **設計器** | ⚠️ 設計標籤是設計行為(對),但**印**是日常操作 —— 目前要印得先進設計器 |
| **動作按鈕 · 簽核定義** | **設計器** | ✅ 對(定義是設計行為),但**沒有任何地方看得到「這張表有哪些自動化」的總覽** |
| Excel 匯入**建新表單** | 設計器 | ✅ 對(那是建表不是填資料) |

### 2.3 沒有「這張表單的全部動作」這個概念

Ragic 的心智是**表單就是操作中心** —— 一個「工具」選單收六組 25+ 動作,
針對這張表的所有事都在這張表上做完。Weyver 目前**沒有這個聚合點**:
使用者得記住「匯出在檢視工具列、標籤在設計器、公開在設定中心」。

## 4. 建議的落點原則(待裁定)

| # | 原則 | 理由 |
|---|---|---|
| **P1** | **粒度決定落點**:per-form 的東西放表單層,per-tenant 的放設定中心 | 這是唯一不會隨功能增加而失效的規則。用「這是設定所以放設定中心」會愈積愈亂 —— 公開表單與通知設定就是這樣進去的 |
| **P2** | **表單層需要一個聚合入口**(對齊 Ragic 的「工具」)| 沒有聚合點,使用者得記住每個動作各自住哪。**但不照抄六組分類** —— 我們只有 11 項,硬分六組會出現只有一項的組 |
| **P3** | **定義留在設計器,執行放到表單層** | 設計標籤 / 定義簽核 / 建按鈕是設計行為;**印標籤 / 送簽 / 按按鈕是日常操作**。目前標籤混在一起,要印得先進設計器 |
| **P4** | 🔴 **搬動入口不得放寬權限** | ⚠️ **原文的推導錯了,2026-08-04 更正**(見 §8)。原則(不得放寬)成立,但「改由該表單的 `design` 權把關」是錯的結論 —— 它假設「原本在 admin 頁面裡」就等於「該用設計權」。**真正的判準是這件事的粒度與擁有者**:公開表單是**租戶級安全決定** → `admin`(後端本來就這樣執法);此表單的通知是**個人訂閱**(`notification_pref` 帶 `actor_id`)→ **不設閘門** |

## 8. 實作紀錄(2026-08-04,第二階段)—— 研究翻掉了原本要做的一半

**已交付**|公開表單與通知的**面板本身**開在表單上(`form-share-panel` / `form-notify-panel`),
不再深連設定中心。沿用 `ImportPanel` 的全接管形態,不新增第三種面板語彙。

### 8.1 一手依據(Ragic 官方,查證 2026-08-04)

| 來源 | 逐字 | 承重的是什麼 |
|---|---|---|
| 設計手冊 `doc/71` | 「在列表頁的**工具**中找到**發佈到網路**」·「同樣可以這個視窗點選 …… **如此一來就不需要進到修改設計中調整**」 | **落點與形態**:per-form 的對外設定開在列表頁「工具」,就地完成。⚠️ **不承重功能對等** —— 它的「發佈到網路」是輸出可下載檔案,與我們的匿名填寫不是同一件事 |
| 使用手冊 `doc-user/12` | 「**表單個別通知** —— 在表單的**工具**選單中的同步與通知選擇**通知設定**」·(同文)個人設定裡另有「**頁籤個別設定**:選擇想要設定通知的表單所在頁籤,針對頁籤中的**個別表單**設定」 | per-form 通知**確實存在**,且**同一筆設定有兩個入口** |

### 8.2 🔴 OQ-IA-3 的做法修正(裁定 A 不變)

當初否決選項 B(雙入口)的理由是「改哪個才算數會變成客訴來源」——
**那個理由只在兩處各存一份時成立**。Ragic 的兩個入口寫的是同一列,不存在歧義。

所以設定中心那一半**不是刪掉**,而是:

| 頁 | 原本 | 現在 |
|---|---|---|
| 公開表單 | 選表單 → 挑欄位 → 建立 + 跨表單清單 + 收件匣 | **跨表單總覽**(含關閉 / 重新開放,租戶級的緊急控制)+ **收件匣**(補上「哪一張表」)。建立在表單上做 |
| 通知 | 軸 1 有一個「選一張表單」的**下拉** | 軸 1 上半 = 全租戶預設;下半 = **逐表單列出**(依分類分組 + 名稱篩選),對齊 Ragic 頁籤個別設定 |

`§2.1` 抱怨的一直是**下拉**,不是「設定中心不該有 per-form 這一層」——
**一次調整我對多張表單的訂閱,是清單才做得到、下拉做不到的事。**

### 8.3 🔴 P4 的權限閘門推導錯了(兩個都錯)

| 入口 | 第一階段(錯) | 現在 | 依據 |
|---|---|---|---|
| 公開表單設定 | `design` | **`admin`** | 後端 `public-form-admin.controller.ts:48` 逐字「開放一張表單給外部人填寫是**租戶級的安全決定,不是表單級功能** → 限 admin」。有 `design` 沒 admin 的人**看得到、按不動** |
| 此表單的通知 | `design` | **不設閘門** | `notification_pref` 帶 `actor_id` = **個人訂閱**;Ragic 也把它寫在**使用手冊**而非設計手冊。用 `design` 擋住等於一般使用者管不了自己的通知 |

**錯在哪**|P4 假設「原本在 admin 頁面裡」就等於「該用設計權」。
真正的判準是**這件事的粒度與擁有者**。

### 8.4 實走(Playwright MCP)抓到兩個斷言看不到的問題

1. **欄位挑選器列出必定被拒的型別**(`autoNumber` / `createdAt`)——
   失敗被留到按下按鈕之後。改由後端回可公開型別(`GET /api/public-forms/safe-types`),
   **前端不維護第二份清單**(兩份會漂移,而漂移的症狀正是這個 bug 的下一次發生)。
   並把「另有 N 個欄位不能公開」講出來 —— 靜默省略會被當成欄位不見了。
2. **逐表單清單在有數十張表單時捲不完** —— 而那是**每個租戶用久了都會到的狀態**。
   依分類分組 + 名稱篩選,達到 Ragic「先選頁籤」的縮小效果,而不再引入一個選一張表單的下拉。

### 8.5 順帶補上的一個陷阱

`scope='form'` 的通知偏好原本**只能設、不能取消** —— 而畫面上寫著「未設定則繼承上層」,
等於承諾了一個到不了的狀態。補 `DELETE /api/notifications/prefs`,
測試專釘「清除 = 回到**繼承**,不是回到系統預設」。
